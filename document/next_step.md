## 1. 追加コマンドの案

優先度は、読み取り専用で効果が大きいものを先にした。各案に「決めること」を付けた。

### 1.0 コマンド一覧 ── `xipe command list`（優先度: 高、基盤）

crux の提案（2026-09-26）。コマンドが増えていく段階なので、使えるコマンドを一覧で出す入口を1つ持つ。人も tezcatl も、ここから辿れるようにする。

- **何をするか**: 2種類の一覧を出す

| 区分 | 出すもの | 出どころ |
|---|---|---|
| CLI のコマンド | `choice project`・`table generate`・`scan`・`show`・`eval`・`do`・`dialogue depends`・`start`・`config`・`refresh`・`help`・`version`（今後の `search`・`rewrite`・`command list` 自身もここ） | `main.exs` に CLI コマンドの表（名前・引数・一行の説明）を作る。`xipe help` もこの表から出せば、2か所で食い違わない |
| `xipe do`・WebSocket の method | `Methods` の表にあるすべて | `lib/methods.exs`。状態（使える／未実装）、読むだけか書くか、REPL を使うかを並べる。一行の説明の欄を表に足す |

- **出力のイメージ**:

```
CLI commands
  choice project <path>        プロジェクトを登録（初回）して選ぶ
  scan [<dir>]                 ソースを読み、カードと link を更新する
  ...
methods (xipe do / WebSocket)
  row/add        write          計算行を作る
  row/list       read           計算行の一覧
  row/update     write, REPL    引数を変えて、その行だけを評価する
  cell/complete  not implemented
  ...
```

- **合わせて**: 同じ表を返す読み取り専用の method（例: `command/list`）を `Methods` に載せる。tezcatl から使えるコマンドの一覧を取れる
- **決めること**: CLI のコマンドの表を作り、`xipe help`（いまは長い説明文を手書き）もそこから出す形にするか。一覧を `xipe command list`（全部）だけにするか、`-c`（CLI のみ）・`-m`（method のみ）で絞れるようにするか

### 1.1 検索 ── `xipe search`（対話で絞り込む、優先度: 高）

2026-09-26 に crux と方針を決めた（案 a「小さな問い合わせ言語」を、対話のターンを重ねる形で実現する）。削除した `affected_set` などの問い合わせ（Old.md §37.3）は、これで表す。結合（join）は問い合わせ言語に持ち込まず、「絞る → 値を取り出す → その値で次を絞る」をターンで重ねる。読み取り専用で、評価も記録もしない（§36 と矛盾しない）。

**流れ**

1. surface table から調べる
2. データベース（`eval_table`）から調べる
3. 得た値を使って、さらに調べる
4. 最後のリストの値に合う行を、指定した列で表示する
5. 対話を終了する

**コマンド（crux 案）**

| 書き方 | 動き | 返り値・メッセージ |
|---|---|---|
| `xipe search -h` | 使い方、surface table の列、`eval_table` の列を表示する。対話は続く | — |
| `xipe search -s\|-e <column> <値> <取り出したい列>` | `-s`（surface table）か `-e`（`eval_table`）で、`<column>` が `<値>` の行を探し、`<取り出したい列>` の値をリストにする | リスト。このリストは検索が終わるまで保持する（`[list]`）。「X件ヒットしました。(得られたリスト)」 |
| `xipe search -s\|-e <column> list` | 保持中の `[list]` の要素ごとに `<column>` を探す | リスト。`[list]` を上書きする。「X件ヒットしました。(得られたリスト)」 |
| `xipe search get id -n` | 保持中のリストの n 番目の ID を取り出す（1から数える、`-n` 無しなら先頭）。取り出した ID は変数 `x` として保持し、対話の中のコマンドで ID の代わりに `x` と書ける | 「検索結果のN番目の要素のIDを取得しました」。範囲外・0件は「No match data」 |
| `xipe search -s\|-e view <column> [列のリスト]` | 保持中のリストの値で `<column>` を探し、当たった行を `[列のリスト]` の列で出力する | 「検索を終了しますか？y/n」 |
| `xipe quit dialogue` | 対話を終える（保持している `[list]` と `x` を捨てる）。search 専用ではなく、対話一般の終了コマンド | — |

**対話の継続（2ビットのタグ、Old.md §17）**

- **終了（`quit dialogue`）を除き、すべて保持する（crux、2026-09-26）**: 検索の各ターンは `view` も含めて `11`（対話を保持し、REPL を介さない）。保持を解放するのは `xipe quit dialogue` だけで、これが `01`。§17 の分類に収まり、新しい種別は要らない。`view` の後の「検索を終了しますか？y/n」は、`y` なら `quit dialogue` と同じ、`n` なら対話を続ける
- **変数 `x`**: `get id` で取り出した ID を保持する1つの枠。次の `get id` で上書きされ、`quit dialogue` で消える。対話の中で打つコマンド（例: `rewrite -prev x 10`）の ID の位置に `x` と書くと、保持中の ID に置き換えてから実行する。検索以外のコマンドも、対話を保持したまま通せる（`InOut` は対話の保持中でも通常のコマンドをそのまま通す作りになっている）
- 状態（`[list]`）を持つ場所は既にある。WebSocket では接続ごとに `Serve.Socket` が対話の状態を持つ（クライアントが1ターンずつ送る形で、プロトコルの上では既に動く）。CLI では `dialogue depends` と同じく `InOut.run_to_completion` で1つのプロセスの中でターンを回す
- **CLI での入り方**: `xipe search` で対話に入り、以降の `-s …`・`get id`・`view` は対話のプロンプトに打つ。シェルから毎回 `xipe search …` を打つと別のプロセスになり、`[list]` は引き継がれない。上の表の `xipe search` の前置きは、対話の中では省いてよい

**`eval_table` の定義**

- surface table から計算行へは、最初のターンで path のリストを得て、それで `-e path list …` と引けば1段で届く（crux）
- そのための前提として、`eval_table` は**計算行（`calls`）に、その関数（`module`・`name`・`anykey`・`effect`）とファイル（`path`）を横付けした1枚の表**とする。いまの Book の計算行は path を持たず、「計算行 → 関数（`nodes`）→ ファイル（`sheets`）」とたどって初めて path に届くため、この横付けを1か所で固定しておく
- 注意: surface table の `id` と Book の `sheets` の id は別物で、両者をつなぐのは `path` だけ
- `eval_table` という名前は `課題.md` §1-5 で「名前だけ決まっていた評価結果の表」。`book.jsonl` の `calls` と役割が重なる、という同項の問いへの答えを、「新しい保存先ではなく、`calls` に横付けした読み取り用の見え方」とする

**使いどころの例**

| 知りたいこと | 対話の流れ（例） |
|---|---|
| あるファイルの関数の計算行 | `-s path lib/calc.ex path` → `-e path list id` → `view` |
| ある行を参照している行（下流） | `-e args ~⟦<id>⟧ id`（部分一致、下記） |
| まだ分類していない関数の計算行 | `-e effect unknown id` |
| 前回から値が変わった行 | `-e compare changed id` |
| 関数がソースから消えた行 | `-e module -`（関数が無い行は横付けの列が空になる）など |

**実装上の注意（決めることではない）**

- 今の対話プログラム（`Dialogue.Depends`）は Book に触らない前提で作られている（必要なデータは開始時に全部渡す）。search はターンごとに Book と surface table を読むので、対話プログラムに読み取り専用のアクセスを渡す口を足す
- 「ある関数を呼んでいる関数」は `links`（呼び出し関係）の検索になる。`-s`・`-e` に加えて3つ目の表（例: `-l`）を持つかは、必要になった時点で決める

**決めたこと（crux、2026-09-26）**

- 値の合わせ方: 既定は完全一致。`~値` と書けば部分一致（下流「`⟦id⟧` を引数に含む行」などに使う）。数値の列（`anykey` など）は文字列の `"2"` と同一視する（住所の解決と同じ）
- `get id -n` の n は1から数える。範囲外・0件のときは「No match data」
- 取り出した ID は変数 `x` として対話の中で保持し、コマンドで ID の代わりに `x` と書ける
- ヒットが多いときは、先頭10件と件数だけを表示する
- 終了コマンドは `xipe quit dialogue`。これ以外のターンはすべて対話を保持する

- コメント:

### 1.2 行の履歴 ── `row/history`（優先度: 高）

- **何をするか**: 1つの計算行の、過去の評価結果を時系列で返す。`book.jsonl` は追記のみなので、同じ id の過去の行がすべて残っている（いまは最後の行だけを「現在の値」として読んでいる）
- **返すもの**: 評価ごとの `result`・`repr`・`compare`・`result_at`・`commit`・`dirty`・`args`
- **意味**: 「Book は時系列の記録」という原則（§36）を、読む側でも活かすコマンド。前回列（`prev`）は直前1回分しか持たないので、それより前を見る手段はこれしか無い
- **決めること**: 引数を変えた前後（`row/update`）を1つの履歴として続けて見せるか、区切って見せるか
- コメント:

### 1.3 surface table を見る・直す ── `surface/list`・`surface/set`・`surface/diff`（優先度: 高）

- **`surface/list`**: 保存済みの table を返す（言語・REPL・ビルドツールの列つき）。言語やパスで絞れるとよい（1.1 の a で代用も可）
- **`surface/diff`**: table と disk の差（table に無い新しいファイル、table にあって消えたファイル）。足したファイルは `xipe table generate` まで読まれない、という仕様（How to use §2.2）を補う
- **`surface/set`**: 行ごとに言語を手で決める（`課題.md` §1-3。`.h` のように2つ以上の言語が申告した拡張子や、拡張子の無いファイル）
- **決めること**: `surface/set` で手で決めた値を、`xipe table generate` の作り直しでどう残すか（`課題.md` に同じ問いがある）。案: table の行に `language_source: "user"` を持たせ、作り直しでは上書きしない
- コメント:

### 1.4 期待値を置く ── `xipe rewrite -prev`（優先度: 中）

- **何をするか**: 計算行の前回列（`prev`）に、利用者が期待値を書く（仕様 §6.4 の「P の出どころが user なら B = P」）。次の評価の `compare` は、この期待値との比較になる
- **書き方（crux 案、2026-09-26）**: `xipe rewrite -prev <id> <任意の値>`。期待値の記述は JSON の更新モジュールを使う
- **形**: Book は追記だけの記録なので、「書き換え」の実体は「`prev` を変えた行を1行追記する」こと（時系列の原則と合う）。中身は `row/set-prev` のようなコマンドとして `Methods` の表に載せ（WebSocket からも使える）、`xipe rewrite` はその CLI の入口にする
- **`rewrite` の範囲**: 「評価せずに Book の値を書き換える」操作の総称にしておけば、将来 `-args`（引数だけを変えて評価しない）なども同じ場所に並べられる。`row/update`（変えて、その行を評価する）との区別もはっきりする
- **値の検査**: 期待値は次の評価で対象言語のソースとして読み戻される。書けない値だと、そのときの `compare` が失敗する。`rewrite` の時点では検査できない（REPL が要る）ので、評価のときに「期待値が読めない」と分かる形で出す
- **現状**: `Core.set_prev/3` は実装済みで、コマンドから呼ぶ手段だけが無い（`課題.md`）
- **決めること**: 期待値は次の評価で上書きされる（仕様 §6.4）。長く持ちたい期待値は別の行に置いて `⟦⟧` で参照する、という仕様のままでよいか。`rewrite` を総称にするか
- コメント:

### 1.5 まとめて分類する ── `effect/set` を住所で（優先度: 中）

- **何をするか**: `effect/set module=Calc effect=pure` のように、住所に当てはまる関数をまとめて分類する。いまは id を1つずつ指定する
- **注意**: 分類は評価の可否を決める安全装置（P1）。まとめて `pure` にするのは危険なので、当てはまった関数の一覧を先に返して確認させる（`dry_run` のような形）か、`pure` だけは1つずつに限るか
- **決めること**: 上の安全策の形
- コメント:

### 1.6 値が古くなった行を示す ── `row/stale`（優先度: 中）

- **何をするか**: 評価した後に、その関数の本体（`body_hash`）や、ロックファイル・flake が変わった行を一覧にする（仕様 §9 の `stale`）。**評価はしない**（§36）。一覧を見て、必要な行を指定して評価し直す
- **必要な変更**: 評価のときに、関数の `body_hash` を計算行に記録する列を足す（いまは記録していない）。ロックファイルは仕様 §9.3 の `git diff --name-only <記録> HEAD -- <ロックファイル>`
- **決めること**: 呼び出し先の関数が変わった場合（依存の変化）も含めるか。含めるなら `links` をたどる（1.1 で表せる）
- コメント:

### 1.7 CLI からの住所の指定と値の書き方（優先度: 中、基盤）

コマンドではないが、コマンドを足すほど効いてくる入力の規則。

- **`graph/neighbors`・`graph/export` を CLI から**: いまは `address` にオブジェクトを渡す必要があり、`xipe do` から使えない。`address.module=Calc` のような「点で区切ったキー」を入れ子の map にする規則を `CommandLine` に足す
- **カンマを含む引数**: `[1,2,3]` を1つの引数として渡せない（`課題.md` §4）。Haskell のタプル `(1,2)` や Elixir のリストで必ず当たる。案: `args:=["[1,2,3]"]` のように、`:=` なら値を JSON として読む
- **決めること**: 上の2つの記法
- コメント:

## 2. 言語ごとの個別対応

### 2.1 言語を1つ足すときに書くもの（共通）

| 部品 | 置き場所 | 中身 |
|---|---|---|
| 言語の申告 | `lib/repl/language/<name>.exs` | `extensions/0`・`repl/0`・`build_tools/0`・`scanner/0`・`adapter/0`・`launch_opts/3` |
| 起動メッセージ | `Launch` 相当 | `argv`・`ready_pattern`（バナー、無ければ `nil`）・`ready_probe`（`XT_READY` を印字させる式）・`exit_input`・`interruptible` |
| 呼び出し式と安全装置 | `EvalTemplate` 相当 | 呼び出し式の組み立て、時間とメモリの上限、repr の判定、`compare`、マーカー付きの印字 |
| 出力の読み取り | `Eval.Scan`・`FieldDrip` 相当 | マーカーの検出、本文のキー＝値の読み取り |
| スキャナー | `Scanner.Lsp` の dialect、または自前の解析器 | 定義（関数）と呼び出し関係。言語サーバーが使えないときの予備も |
| scripts-mode の安全な読み込み | `SourceSanitize` 相当 | ビルドツールが無い対象で、ファイルのトップレベルの副作用を実行せずに読み込む方法 |
| 実機テスト | `test/live/` | Elixir 版（`repl_iex_test.exs`）と同じ構成 |

書き方の詳細は `repl-adapter-guide.md`、値の形の問題は Old.md §30（`embody`）。

### 2.2 どの言語でも当たる論点

1. **参照の値を埋め込むときは括弧で包む**: `⟦id⟧` の値はテキストのまま引数に埋め込む（`exact`）。Haskell・OCaml では `f -1` が引き算として読まれるなど、埋め込んだ値が式の結合を変えうる。値は常に `( … )` で包むのが安全（Lisp 系は不要）
2. **arity と `anykey`**: Elixir は arity で同名の関数を区別し、`anykey` に arity を入れて `row/add` の引数の数を検査している。カリー化する言語（Haskell・OCaml）では arity に意味が薄く、Clojure・Racket は複数の arity を1つの名前にまとめる。これらでは `anykey` を `nil`（名前だけで一意）にし、引数の数の検査は効かない。代わりに型（Haskell の型シグネチャ、言語サーバーの hover）から引数の数を取る手もある
3. **公開されていない関数**: Elixir の `defp` は計算行にできない。他の言語では「読み込み方によっては呼べる」ことが多い（下の各言語を参照）。計算行にできるかどうかは、言語ごとに `visibility` の意味を決める
4. **遅延評価と例外の時機**: 値を強制しないと例外が評価の外で起きる（Haskell）。repr を判定する前に、印字する範囲まで値を強制する
5. **時間とメモリの上限**: Elixir は `spawn_monitor` と `max_heap_size` で1件ずつ区切っている。言語ごとに使える仕組みが違い、メモリの上限は持てない言語もある（その場合は REPL ごと kill する既存の経路に頼る）
6. **値の形（repr）**: 往復検査（文字列にして読み戻す）ができる言語とできない言語がある。できない言語は `embody`（Old.md §30）で「有限の表示文字列＋`repr=unsupported`」に落とす。**Lisp 系から始めるとこの問題が見えないまま進む**（§30.1）
7. **1回の評価ごとに REPL を起動する費用**: セッションは常駐しない（§35）。JVM（Clojure）やビルドの重い構成（`stack ghci`・`dune utop`）では起動が数秒以上かかりうる。起動時間を実測し、許容範囲かを確かめる
8. **副作用の分類の手がかり**: 型が副作用を表す言語（Haskell の `IO`）では、分類（`effect/set`）の提案に使える。ただし採用は利用者の明示だけ（P4、`effect_source: user`）
9. **引数の書き方と CLI**: 引数は対象言語のソースで書く。カンマ区切りの規則（1.7）と衝突する言語がある（Haskell のタプル・リスト）
10. **言語が混ざるプロジェクト**: 2026-09-26 に「1回の評価は1つの言語」という仮の制限を外した（2.6、Old.md §39）。行は言語ごとの REPL で評価される。言語をまたぐ参照と、FFI や JVM 相互運用で言語が混ざる対象（Haskell＋C、Clojure＋Java）の依存の記録は、2.6 と境界規則（仕様 §13）の話

### 2.3 言語ごとの留意点

**基本方針（crux、2026-09-26）: REPL は素のものを使う。** 言語ごとに REPL を1つに決め、ビルドツールは起動の仕方だけを変える（`Repl.Language` の申告どおり）。Haskell で GHCi を選んだのは、`stack`・`cabal` のどちらを経ても最後は GHCi につながるから。アダプタ（呼び出し式・出力の読み取りなど）は REPL 1つにつき1組で済む。

以下は知識にもとづく下書きで、**この環境ではどの処理系も実機で確かめていない**（`repl-adapter-guide.md` の「候補言語ごとのチェックリスト回答」と同じ扱い）。実装前に、対象の flake 環境で1つずつ裏を取る。

#### Haskell（GHCi）

| 論点 | 留意点 |
|---|---|
| ビルドツールの申告 | `stack`（`stack.yaml`）> `cabal`（`*.cabal`、`cabal.project`）> なし。起動はそれぞれ `stack ghci`・`cabal repl`・`ghci`。**どれも中身は GHCi** なので、アダプタは GHCi 用の1組でよい |
| scripts-mode | `ghci file.hs` はモジュールを読み込むだけで `main` を実行しない。トップレベルの副作用が無い言語なので、`SourceSanitize` 相当は不要の見込み |
| 起動の確認 | プロンプトが読み込んだモジュールで変わるので、バナーは `nil` にして `ready_probe`（`putStrLn ("XT_" ++ "READY")`）だけにするのが確実 |
| 呼び出し式 | `M.f (a) (b)`。修飾名には `import qualified` が要る。GHCi は型の既定化（`ExtendedDefaultRules`）をするので、`f 1` の型が意図と変わりうる。必要なら引数に型注釈を書いてもらう |
| 公開されていない関数 | `:load *Module`（解釈実行で読み込む）なら export されていない関数も呼べる。`cabal repl` の既定の読み込み方で呼べるかは要確認 |
| 値の形 | `Read` を持つ型は少ないので往復検査はほぼ使えない。`embody` の `observe`（`show` の出力を有限に切る、Old.md §30.3）が本線。無限構造も `show` の遅延評価で先頭だけ取れる |
| 遅延評価 | `evaluate` と表示範囲までの強制が必要。例外は強制した時点で起きる |
| `IO` を返す関数 | GHCi は `IO a` の式を実行してしまう。`IO` を返す関数は `pure` にできない（分類の提案に使える） |
| 上限 | 時間は `System.Timeout.timeout`（割り当てをしないループは止まらないことがある）。メモリは `enableAllocationLimit`（スレッドごとの割り当て上限）が使える見込み |
| 言語サーバー | HLS（haskell-language-server）。`documentSymbol`・`callHierarchy` ともに対応している見込み。起動が重い |
| arity | カリー化のため `anykey` は `nil`。同じモジュールに同名の関数は置けないので、名前だけで一意 |

#### OCaml（素の `ocaml` トップレベル）

| 論点 | 留意点 |
|---|---|
| ビルドツールの申告 | `dune`（`dune-project`）> なし。REPL は素の `ocaml` に揃える（Haskell の GHCi と同じ考え方、`utop` は使わない。`utop` の行編集と pipe の相性の心配も無くなる）。dune のプロジェクトでは、`dune ocaml top` が出力する「プロジェクトのライブラリを読み込む指示」を素の `ocaml` に読ませる（`#use_output "dune ocaml top";;` の形、要確認） |
| scripts-mode | `#use`・`#mod_use` はトップレベルの `let () = …` を実行する（**確認済み**）。副作用を避けるには `SourceSanitize` 相当（トップレベルの式を除く）が要る |
| 起動の確認 | バナーは版で変わる。`ready_probe`（`print_endline ("XT_" ^ "READY");;`）を主にする。文の終わりに `;;` が要る |
| 呼び出し式 | `M.f (a) (b)`。`f -1` が引き算になるので値は括弧で包む（2.2-1） |
| 公開されていない関数 | `.mli` で隠れた関数は、ライブラリとして読み込むと呼べない。`#use` でソースを直接読めば呼べる |
| 値の形（**確認済み**、2026-09-26） | 固定の `embody.ml` が、式のテキストをトップレベル自身の仕組み（`Toploop.execute_phrase`）で評価し、トップレベルの表示 `val xt_<id> : 型 = 値` を文字列として受け取る（2.5、Old.md §38）。型が一緒に取れ、表示は必ず有限（循環は `<cycle>`、関数は `<fun>`）。表示をもう一度評価して `=` で比べれば往復検査もできる見込み |
| 同名の関数 | 同じモジュールで同名の `let` を重ねて書ける（後ろが前を隠す）。自然キー（モジュール・名前）が一意にならないので、`anykey` に出現順を入れるなどの工夫が要る |
| 上限 | 時間は `Unix.alarm`＋シグナル、またはスレッド。トップレベルに `unix` ライブラリを読み込む必要がある。メモリの上限は難しく、REPL ごと kill に頼る見込み |
| 言語サーバー | ocaml-lsp（`ocamllsp`）。`documentSymbol` は対応。`callHierarchy` の対応は要確認 |

#### Java・Python（関数型以外、参考）

作ろうと思えば作れる。REPL（`jshell`・`python`）があり、「REPL を起動し、式を送って、マーカー付きの出力を読む」という xipe の形には乗る。ただし関数型言語より合わない点がはっきりある。

| 言語 | 乗る点 | 合わない点・注意 |
|---|---|---|
| Python | `python -i`。モジュールの関数を `mod.f(a)` で呼べる。`repr()` と `ast.literal_eval` で基本的な値は往復検査できる。pyright などの言語サーバーは `callHierarchy` を持つ | 副作用のある関数が普通なので、分類（`effect/set`）の比重が大きい。1件ごとの時間の上限は `signal.alarm` で取れるが、メモリの上限はプロセス全体にしか掛けられない。スクリプトはトップレベルで処理を走らせるのが普通なので、関数定義だけを読み込む工夫が要る（`SourceSanitize` 相当） |
| Java | `jshell`。static メソッドなら `Class.m(a)` で呼べる。Maven・Gradle は `--class-path` を渡す起動方法の違いとして申告できる。jdtls は `callHierarchy` を持つ | 計算行は「関数を1回呼ぶ」ものなので、インスタンスメソッドはオブジェクトを作らないと呼べず、そのままでは乗らない（static に限る、など範囲の決めが要る）。値を読み戻す汎用の仕組みが無い（`toString` だけ）ので `embody` の考え方が要る。JVM の起動が重く、評価のたびに起動する方針（§35）では遅い |

### 2.4 着手順

**決定（crux、2026-09-26）: Haskell と OCaml を優先する。** どちらも往復検査の汎用の仕組みが無く、値の形（`embody`、Old.md §30）に最初から向き合う順番になる。Old.md §30.1 の注意（Lisp 系から始めると repr の問題が見えないまま進む）にも沿う。Clojure・Racket はその後。

検討した案（参考）:

| 案 | 順序 | 考え方 |
|---|---|---|
| A | Erlang → Haskell → Clojure/Racket → OCaml | Erlang で「言語を1つ足す」手順を最小の費用で一度通してから、難しい値の形に当たる |
| B | Haskell → Clojure/Racket → OCaml | 本命の関数型言語から始め、最初から `embody` を作る |
| **採用** | **Haskell → OCaml →（Clojure・Racket）** | B に近い。ML 系の2言語で `embody` と素の REPL の方針を固める |

**Haskell の最初の一歩（案）**:

1. GHC の入った環境（`nix shell nixpkgs#ghc`、または GHC を入れた検証用の flake）で、GHCi を pipe でつないで裏を取る。確かめる点: `putStrLn ("XT_" ++ "READY")` での起動確認、プロンプトの扱い、`:load *Module` で export されていない関数を呼べるか、`System.Timeout.timeout` と `enableAllocationLimit` で1件ずつ区切れるか、SIGINT で評価だけが止まるか（`interruptible`）
2. `embody` の `observe`（Old.md §30.3）を、`field_drip` の書式と `compare` に合わせて書く
3. `Repl.Language.Haskell`（申告）→ アダプタ4つ → 実機テスト（`test/live/` に GHCi 版）の順で作る
4. スキャナーは、まず HLS の dialect（`Scanner.Lsp`）を試し、使えないときの予備を決める

### 2.5 `embody` による実行手順（Haskell・OCaml 共通、2026-09-26）

**xipe_totec から見た手順は、Haskell でも OCaml でも同じ**（crux）。関数 A を見たいときは A の計算行を作って評価するだけで、依存の深さのある評価は計算行を `⟦id⟧` でつないで指定する。言語による違いは、アダプタが送る1行と `embody` の中身に収まる。

- **`embody` はアダプタが毎回自動で包む**: 利用者が行ごとに指定するのではなく、その言語の `EvalTemplate` 相当が、評価する呼び出しを必ず `embody` で包んで送る（Elixir 版がどの行も安全装置で包むのと同じ位置づけ）
- **`embody` は対象を知らない固定のモジュール**: どの関数を包むかは、送る1行が決める（Old.md §30.3）。対象への依存は、`embody` のコンパイル時ではなく、REPL が実行時に解決する（コンパイル時に依存させると対象ごとに作り直しが要り、型の知識も要る。§30.2 で退けた形になる）

| 言語 | アダプタが送る1行（イメージ） |
|---|---|
| Haskell | `let xt_<id> = M.a (x)` の後に `Embody.observe "<id>" <上限> xt_<id>` |
| OCaml | `Embody.run "let xt_<id> = M.a (x);;"`（`Toploop.execute_phrase` が評価し、表示を捕まえる） |

- **依存の連鎖（embody → A → …）**: `⟦id⟧` でつないだ計算行を並べて指定する（How to use §2.6、Old.md §36）。依存の順に1行ずつ `embody` で包んで評価し、どの段も記録される。前の段の結果は同じ評価の中では変数 `xt_<id>` で渡るので、表示では読み戻せない値（関数・循環する構造）でも連鎖の途中を通せる（OCaml でトップレベルの束縛が次の段から見えることは確認済み）。評価をまたいで使えるのは、読み戻せた（`exact`）値だけ
- **入れ子の式で書く方法もある**: A の引数に `M.b (M.c 1)` のように直接書けば、記録されるのは A だけで、B・C は A の入力の計算として実行される（利用者が書いた式なので「勝手な評価」ではない）。段ごとに見たいなら計算行の連鎖、入力を作るだけなら入れ子の式

**言語ごとに残る違い**

| 論点 | Haskell | OCaml |
|---|---|---|
| scripts-mode の安全な読み込み | 不要の見込み（トップレベルに副作用が無い） | 必要（確認済み） |
| 1件ごとの時間の上限 | `System.Timeout.timeout` | `Unix.alarm` など（未確認） |
| 1件ごとのメモリの上限 | `enableAllocationLimit`（未確認） | 難しい（REPL ごと kill に頼る見込み） |
| 往復検査 | `Read` を持つ型に限られる | 表示を再評価して `=` で比べる（見込み） |
| 型の取得 | `:t` などで別に取る | 表示に付いてくる（確認済み） |
| 表示の有限性 | `show` の出力を途中で切る（§30.3） | トップレベルの表示が深さと長さで打ち切る（確認済み） |

### 2.6 言語が混ざるプロジェクト（例: `.exs` が `.ml` に依存する）

Aepyornis（Elixir の `lib/` が、dune でビルドした OCaml の実行ファイルを Port で呼ぶ）のような構成。

| 層 | いまの動き |
|---|---|
| surface table・スキャン | 動く。言語ごとに行が分かれ、それぞれの言語のスキャナーが読む |
| 評価 | **動く（2026-09-26、仮の制限を外した、Old.md §39）**。指定された行を、関数 → ファイル → surface の `language` とたどって言語ごとに分け、言語ごとに REPL を起動して並行して評価する。言語をまたぐ `⟦id⟧` 参照だけは `not run`（理由付き）。以前は、評価する言語をプロジェクト全体の table から1つに決めていたため、言語が2つあるだけで OCaml の行だけを指定しても拒否されていた（OCaml の部分を別プロジェクトとして登録すれば評価できた） |
| Elixir の関数が OCaml を呼ぶ部分 | 評価そのものは動く見込み。iex の中で Elixir の関数が Port で OCaml の実行ファイルを起動するだけなので、xipe から見ればその関数の副作用（`reads`/`writes` の分類）。ただし OCaml 側を先にビルドしておく必要があり（xipe はビルドしない）、実行ファイルが環境（flake、How to use §4.3）から見える必要がある |
| 言語をまたぐ依存の記録 | 無い。Elixir → OCaml の呼び出しは `links` に載らず、OCaml 側が変わっても Elixir の行は古い（stale）と分からない。仕様 §13 の境界規則（Rustler の例と同じ枠）の話 |

**値の書き方**: 値は各言語の REPL が出した表示のテキストのまま Book に保存し、`⟦id⟧` の参照もそのテキストを加工せずに貼るだけ。xipe_totec が独自の書き方に直したり、言語どうしで自動で変換したりはしていない（crux の方針「値の書き方は xipe_totec の上でも言語に合わせる」と一致）。そのため、言語をまたぐ参照はそのままでは使えない（OCaml の `[1; 2]` を Elixir の式に貼ると構文エラー）。

**言語をまたぐ依存の連鎖（設計、未実装、2026-09-26 crux と）**

混合言語プロジェクト向けに、言語をまたぐ依存の連鎖を評価の対象にするとき、間に変換を挟む。

- **変換が要るかは、計画の時点で決まる**: 評価の計画（`Core.plan_recalc`）を立てる時点で、指定された行と `⟦id⟧` の連鎖、各行の言語（カードの関数 → ファイル → surface の `language`）が分かっている。参照元と参照先の言語が違えば、その間に「変換の段」を差し込んでおき、評価のときにそこで変換プロトコルを通す
- **どの変換かは、型で割り当てる（crux）**: 計算行には `result_type` 列があり（`eval_table` にも載る）、評価のたびに値の型が記録される。**型ごとに変換モジュールを用意し、型で割り当てる**。参照先が以前に評価済みなら記録された型で計画の時点に、同じ評価の中で初めて評価される場合でも結果と一緒に型が届くので、参照元を評価する前に決まる
- **型の記録の細かさは言語で違う**: OCaml は `Target.shape list` のように中身まで含めた型が取れる（トップレベルの表示、確認済み）。Elixir は `integer`・`binary`・`list`・`map`・`tuple`・構造体の名前という粗い分類（`EvalTemplate`）
- **向きによる違い**: 型の細かい言語 → Elixir は、参照先の型だけで選べる（Elixir 側は値の書き方が中身を表すので要素は値を見て変換できる）。Elixir → OCaml・Haskell は、基本の型なら参照先の型で足りるが、map をレコードやヴァリアントにするには**受け取る側の型**（参照元の関数の引数の型、カードの関数の情報や言語サーバーの hover から取る）も割り当ての鍵に要る
- **対応表の鍵は「言語と型の名前の組」**（型の名前は言語ごとに違う、Elixir の `integer` と OCaml の `int`）。言語の組ごとの変換（n²）ではなく、中立の形（JSON のような: 整数・文字列・リスト・レコード・タグ付きの値・バイト列）を真ん中に置き、各言語は「表示テキスト → 中立」「中立 → ソースの書き方」の2つを持つ

| 鍵 | 変換モジュール |
|---|---|
| (OCaml, `int`) → Elixir | 整数（xipe が用意） |
| (OCaml, `'a list`) → Elixir | リスト（要素はそれぞれの型で再帰的に変換） |
| (Elixir, `binary`) → OCaml | 文字列（xipe が用意） |
| (OCaml, `Target.shape`) → Elixir | 利用者が登録（ヴァリアントを Elixir でどう書くか） |
| (Elixir, `map`) → OCaml の `Target.rect` | 利用者が登録（受け取る側の型が鍵に入る） |

- **分担**: 基本の型とコンテナの変換は xipe が用意し、プロジェクト固有の型（OCaml のヴァリアント・レコード、Elixir の構造体）は利用者が登録する
- **登録の規律**（Aepyornis の `conversion_table` と同じ）: 追記だけで番号を振り直さない。**登録されていない型は黙って既定値で埋めずにエラー**（その参照は `skipped`、理由付き）。登録は手動の CLI（`rewrite` と同じ JSON 更新モジュール、1.4）
- **方針との整合**: Book に保存する値は各言語の書き方のまま。変換するのは境界をまたいで渡すその瞬間だけ。変換は評価ではないので §36 にも反しない。ただし参照元の記録に「入力が言語の変換を経て来た」ことを残す列（注意の表示）はあった方がよい
- **評価の流れ**: 言語ごとの REPL を評価の間だけ並べて動かし、依存の順に「参照先の言語の REPL で評価 → 変換 → 参照元の言語の REPL へ渡す」。依存の無い言語グループどうしは並行のまま
- **プログラム自身の境界とは別**: Aepyornis の中で Elixir が Port で OCaml を呼ぶのはプログラム自身の境界で、iex の中で完結するので xipe の変換は要らない（要るのは下の境界規則）。この対応表は、**xipe の上で言語の違う計算行どうしをつなぐとき**のもの

**境界規則（残り）**: Port で呼ぶ実行ファイル（dune の `bin/*.ml`）と Elixir 側の呼び出し箇所を結ぶ `links` と、OCaml 側の変更で Elixir の行を stale にする仕組み（仕様 §13）。1.6 の `row/stale` と合わせて考える。

- **決めること**: 変換の対応表を作る時期（Haskell・OCaml の対応と並行か、後か）。参照元の記録に「変換を経た」印を付ける列の形
