1. 目的と位置づけ

表計算ソフトでは、すべての値がセルという住所を持ち、数式は住所への参照で結ばれ、シート名を変えれば参照が追従する。任意の数セルを指定して検算でき、上流の値を変えれば下流が再計算される。その根にあるのは、キーで結ばれたテーブル群というリレーショナルな構造である。Xipe Totec はこの構造を、関数型言語で書かれたプロジェクトに持ち込む。

出発点は、対話環境（REPL）で関数を試すときの手間である。入力値を毎回手で打つ、ファイルパスを指定する、といった操作を、保存された呼び出しとして再利用できるようにする。これを計算行と呼ぶ（第4章）。計算行の引数には、別の計算行の出力への参照を置ける。

もう一つの柱は連動修正である。カード上で関数名やファイル名を変更すると、その変更が対象プロジェクトのソース（定義側）に反映され、さらにそれを参照している他のモジュールのソース（参照側）にも反映される。

加えて、実行中のプログラムの関数呼び出しを動作順に1つの表として記録し、計算行の入力候補として使えるようにする（第5章）。

Xipe Totec は、言語に依存しない基本構造、言語ごとのREPLアダプタ、言語の境界ごとの境界規則から成る。単独で動くローカルサーバー兼CLIとして提供する。利用者はコマンドでカードの計算行を用意・編集・削除し、評価するとテーブルが更新されていく。表示と入力の操作はクライアントが担い、クライアントは外部プロセスとして接続する。

1.1 非目標

  • IDE やエディタの置き換え。表の表示、セルの移動、ハイライト、補完候補の表示などはクライアントの責務とする。
  • LLM 向けのコード索引（読み取り専用の文脈供給）。これは既存の tree-sitter 系 MCP サーバー群の領域であり、Xipe Totec は「値」と「書き戻し」を加える点に独自性を置く。
  • 汎用の実行時ロガーやプロファイラ。実行時の記録は、関数の入出力と呼び出し順に限る。
  • 判定式など、コードの中身そのものの編集。
  • マクロを計算行の評価対象とすること。
  • 評価のサンドボックス化。副作用の判定を誤れば、書き込みは実際に起こる（第8章）。
  • 汎用リファクタリングツールとしての網羅性。

2. 設計原則

P1 参照透明性を前提とする。 対象関数は原則として参照透明であるとみなす。この前提により、計算行の（引数, 出力）は「いつ見ても変わらない事実」として扱える。副作用を持つ関数やセル式は明示的に区別する（第8章）。

P2 再現性を最優先する。 保存物には生成元の内容ハッシュと git のコミットを付与する。修正処理は「ブック＋編集イベント → 修正リスト」という純粋関数として定義する。解析結果には、それを得た提供元を記録する。

P3 IDと名前を分離する。 シート（ファイル）、関数、計算行はすべて名前とは独立した不変IDを持つ。IDは代理キー、名前は自然キーにあたる。セル内の参照もIDで保存する。

P4 非対称な信頼。 LLM やヒューリスティクス、外部の提供元は「提案」のみを行う。LLM が生成したREPLアダプタや、クライアントが提供する解析結果も、受け入れ検査に合格したものだけを採用する。自動判定の結果は、利用者がテーブル上で確認・更新できる。

P5 差分は追加部分に閉じ込める。 基本構造（テーブル、ID、参照解決、再計算順序、修正計算）は言語非依存とする。言語ごとの差はREPLアダプタに、言語の境界をまたぐ対応は境界規則に置く。

P6 書き込みは必ず diff → apply の二段階。 ソースファイルへの変更は、修正リストのプレビューを経てから適用する。

P7 入力体験はクライアントの責務。 サーバーは補完候補、参照の解決結果、行単位の変更通知を返す口を提供する。表示や入力の方法はクライアントが定める。

P8 単体で完結し、外部の提供は上乗せとする。 名前解決と構文解析は、Xipe Totec 単体で動く基本動作を持つ。言語サーバーやクライアントの提供する解析は、機能ごとに対応を確認したうえで優先して使う（第11章）。

P9 判定しきれないものは表に出す。 副作用、依存の完全性、値の忠実度など、自動では確定できないものは、推定値と状態をテーブルの列として示し、利用者の確認に委ねる。

P10 対象プロジェクトの環境で動かす。 評価、トレース、判定式とセルの式の構文解析は、対象プロジェクトの環境にある REPL の中で行う。Xipe Totec 自身の実行環境は、対象言語のバージョンと無関係に保つ。

同じ行に並んだセル同士に意味上の結びつきはない。セル間の関係を作るのは参照だけであり、行は配置にすぎない。意味上の対応を持つのは、節ごとの「判定式と送信先」の組だけである。受信元は関数単位の独立した一覧である。

5. 実行時観測（trace 表）

5.1 考え方

実行中のプログラムで呼ばれた関数を、シートをまたいで動作順に1つの表へ積む。呼ばれるはずで呼ばれなかったものも no_data として記録し、「何が起きなかったか」も表から読めるようにする。

5.2 列

pid 呼び出しが起きたプロセス（言語によってはスレッド等）
seq プロセス内での順序番号
ts タイムスタンプ（プロセスをまたいだ並びの参考）

5.3 順序と no_data

順序：並行実行する言語（BEAM など）では、全体を一列に並べる順序は定まらない。行のキーは (run, pid, seq) とし、プロセスをまたいだ並びは ts による参考情報とする。

no_data は2種類ある。

  1. 飛ばされた送信先：ある関数の呼び出しから戻りまでの区間に、その関数のリンク行の送信先が現れなかった場合、戻りの時点に送信先ごとの no_data 行を置く。判定は呼び出し・戻りイベントの区間だけで行う。
  2. 一度も呼ばれなかった関数：node と trace の左外部結合で NULL として現れる。保存せず、ビューとして提供する。

5.4 記録の方法

Tracer は、対象プロジェクトの REPL セッションに小さな記録用モジュールを読み込ませ、呼び出し・戻りのトレースを設定する（P10）。BEAM では標準のトレース機構を使う。記録開始時に run を発行し、そのときのコミットと dirty を run に記録する。

境界の先（NIF など）の呼び出しは記録できないことがある。その場合、境界の手前のスタブ関数の呼び出しだけが残り、関数の trace_coverage を partial とする（第13章）。

5.5 計算行への取り込み

observed の行を選んで call に追加する。

INSERT INTO call (node, args, origin)
SELECT DISTINCT node, args, 'trace'
FROM trace
WHERE run = :run AND status = 'observed' AND node = :node;
  • 同じ (node, args) の計算行が既にある場合は追加しない。
  • 取り込んだ行は改めて評価し、結果と state を確定する。trace の結果は参考値とする。
  • no_data と raised の行は取り込みの対象外とする。

5.6 記録量と保持期間

記録量と保持期間は用途によって変わるため、固定値を定めずパラメータとする（第17章）。記録負荷は主に記録対象の範囲（trace.scope）で調整する。trace.max_rows は、記録側が処理しきれずに実行中のシステムが重くなるのを防ぐ安全装置であり、到達した時点で記録を自動停止する。

6. 住所、参照、評価

6.1 住所

住所は区切り文字でつないだ文字列ではなく、列の組として扱う。すべての列は任意の条件であり、組み合わせて絞り込む。一意に決まればその対象を返し、複数該当すれば候補を返す。

列 内容
file ファイルパス
module モジュール名
name 関数名
arity 引数の数（引数の数で関数を区別する言語のみ）
type 型による絞り込み。type だけを条件にすると、型に合う関数の逆引きになる
hier 階層コード（前方一致）
row 計算行のID
  • サーバーインターフェースでは、住所をオブジェクトとして送受信する（例：{"file": "lib/shop/price.ex", "name": "add_tax", "arity": 2}）。
  • CLI では列ごとのオプションで指定する（第15章）。
  • 人が読む文字列としての書式は定めない。表示の仕方はクライアントが決める。

6.2 参照

セル内の参照は ⟦計算行のID⟧ の形で書き、他の計算行の結果全体を指す。記号は対象言語の構文と衝突しないことを優先して選んだ。人が読む名前は、クライアントが ID から引いて表示する。

出力の一部を取り出す場合は、対象言語の式で書く。Xipe Totec 独自の取り出し記法は設けない。

elem(⟦c_01H9A0…⟧, 1)
with {:ok, x} <- ⟦c_01H9A0…⟧, do: x
hd(⟦c_01H9A7…⟧.items)

参照は ID で保存されているため、名前変更の際に書き換える必要はない。セルの式に名前が直接書かれている場合（Shop.Price.add_tax(...)）は、ソースと同じく連動修正の対象になる。

6.3 値の受け渡しと忠実度

評価は止めずに行い、結果をどこまで忠実に表せたかを repr 列に示す（P9）。

repr 意味 例
exact 正規形の文字列で完全に表せた 数値、文字列、タプル、マップ
binary 外部項形式で完全に保存した。表示用の文字列を併記する 表示が省略形の構造体、大きな値
unsupported 保存も再現もできない。表示用の文字列だけ残る 無名関数、PID、参照、ポート

参照先の渡し方は次のとおりとする。

参照先の repr 参照先の関数の effect 渡し方 再現性
exact 問わない 正規形の文字列を式に埋め込む あり
binary 問わない 外部項形式から復元して渡す あり
unsupported pure 参照先の呼び出し式をそのまま埋め込む あり
unsupported pure 以外 セッション内の変数に束縛して渡す なし（unreproducible）
  • unsupported の場合、result_type 列に原因の型を示す。Xipe Totec で確認した結果と実際の値に差異がありうることを、表から読み取れるようにする。
  • セッション内の束縛は高速化のためのキャッシュとしても使ってよい。消えていた場合は、式の埋め込みに戻す。
  • セッションが再起動して束縛が失われた場合、それに依存する計算行は lost とする。lost の計算行は自動では再評価しない。
  • binary の値は、構造体の定義が変われば中身が合わなくなりうる。この変化は dep_hash の変化（第9章）として検出され、計算行は stale になる。

6.4 評価の手順と前回列

1回の評価は次の手順で行う。評価直前の結果を R_old、前回列を P とする。

  1. 比較の基準 B を決める。P の出どころが user（利用者が書いた期待値）なら B = P、そうでなければ B = R_old。
  2. 参照を解決し、新しい結果 R_new を得る。
  3. B が空なら compare = none。repr が unsupported、または state がエラー値なら compare = skipped。それ以外は、REPLアダプタの比較機能で R_new と B を比べ、same または changed とする。
  4. 前回列を R_old で上書きする（R_old が空なら B を残す）。prev_source は auto、prev_at は R_old の評価日時とする。
  5. 結果列を R_new とし、result_at、commit、commit_at、dirty、session を更新する。eval_count を1増やす。

前回列は評価のたびに直前の結果で上書きされる。changed の表示は次の評価で消えるが、前回列と結果列の日時から、いつ変わったかを追える。長く保持したい期待値は、別の計算行に置いて ⟦ ⟧ で参照する。

6.5 エラー値

state 表計算の対応 例
ref_error #REF! 参照先の関数や計算行が消えた
eval_error #VALUE! / #N/A 例外、パターン不一致、時間切れ、メモリ上限超過
cycle 循環参照の警告 計算行同士が互いの結果を参照している
unreproducible （なし） 実行ごとに変わる値、セッション内の束縛で受け取った値を含む
stale （なし） 評価後に依存先のコードや実行環境が変わった（第9章）
lost （なし） セッションの再起動で、依存していた束縛が失われた

エラー値を参照したセルもエラー値になり、下流に伝わる。最初に壊れた計算行は、伝播の起点をたどって特定できる。

6.6 再計算

  • 参照の依存順に評価する。循環参照は検出して cycle とする。
  • 全体の再計算の対象は、effect が pure または reads の関数の計算行とする。reads の結果は unreproducible とする。writes と unknown は、明示的に指定した場合だけ評価する。
  • call_hash が保存値と同じ計算行は、評価を省略して保存済みの結果を使える（第9章）。

7. ID方針

7.1 付与

シート、関数、計算行、run は、初回の登録時にIDを付与される。IDは時刻順にソート可能な一意値（ULID等）とし、名前やパスから導出しない。IDが同一性の本体である。

7.2 階層コード

ディレクトリ・ファイル・モジュール・関数の各階層に、2桁の番号を振る（例：03.12.01.05）。

  • 番号は初回の登録時に振り、振り直さない。新しく現れた要素には、その階層の空き番号を与える。
  • 1つの階層に100を超える要素がある場合は、その階層だけ桁を広げる。
  • 別の親へ移動した要素は、移動先の階層で番号を振り直す。

階層コードは、再スキャン時の照合の手がかりと、人が読める短い住所（6.1節の hier 列）を兼ねる。ソース上の行番号がずれても変わらない。

7.3 再スキャン時の照合

再スキャンでは、既存の関数と新しく解析された関数を照合し、同一とみなせるものには既存IDを引き継ぐ。Xipe Totec の外で名前が変更された場合に「削除＋新規」と誤認しないことが目的である。

変化 階層コード body_hash 名前 判定
名前だけ変わった 一致 一致 不一致 同一（名前変更）
本体だけ変わった 一致 不一致 一致 同一（編集）
別ファイルへ移動 不一致 一致 問わない 同一（移動）
名前も本体も変わった 一致 不一致 不一致 needs_review
どれも一致しない – – – 削除＋新規

照合結果が曖昧な場合は自動で決めず、needs_review としてクライアントに提示する。

7.4 墓標

消失した関数は即削除せず、tombstone として保持する。後の照合で名前変更や移動と判明した場合に、IDと計算行を引き継いでつなぎ直すためである。墓標の完全削除は clean コマンドで明示的に行う。墓標になった関数を参照している計算行は ref_error になる。trace の行は墓標になった関数を指したまま残す。

8. 副作用

8.1 区分

effect 意味 例（Elixir） 何度実行しても安全か 結果は再現するか
pure 副作用なし 通常の計算 安全 する
reads 外界に依存する 時刻・乱数、Application.get_env、ファイルの読み込み、ETS の参照 安全 しない
writes 外界を変える ファイル書き込み、send・spawn、GenServer 呼び出し、ETS への書き込み、ログ出力 危険 –
unknown 判定できなかった 動的呼び出し、変数で渡された関数、NIF 不明 不明

副作用の判定が重要になるのは、主に全体の再計算である。利用者が個別に選んで評価する場合と違い、判定に反映されていない副作用のある関数が巻き込まれうるためである。

8.2 自動判定（提案）

  1. REPLアダプタが、副作用を持つ基本関数の表を提供する（Elixir なら File、IO、System、:ets、send など）。
  2. link に沿って伝播させる。呼び出し先に writes があれば writes、reads があれば reads、すべて pure なら pure とする。
  3. 標準の高階関数（Enum.map など）は「引数の関数の副作用を引き継ぐ」と表に定義し、渡される関数が特定できる場合は中身を調べる。特定できない場合は unknown とする。
  4. 依存ライブラリは、ソースがあれば同じ方法で解析し、ロックファイルの版ごとに結果をキャッシュする。

8.3 確認と更新

  • 自動判定の結果は effect_source = inferred として node に入る。
  • 利用者はテーブル上で effect を更新できる。更新した値は effect_source = user となり、再スキャンで上書きしない。
  • 評価中に副作用の基本関数の呼び出しを監視し、判定と実際の動作が食い違った場合は needs_review として知らせる。この監視は実行後に分かる方法なので、事故の防止ではなく判定の検証に用いる。
  • 判定はソースに書き込まない。

9. 依存込みハッシュ

9.1 目的

計算行の保存済みの結果がまだ正しいか（stale の判定）と、どの計算行を再計算すればよいかを決める。

9.2 ソースの依存

dep_hash(f)  = H( body_hash(f), 呼び出し先 g すべての dep_hash(g)（ID順） )
call_hash(c) = H( dep_hash(c の関数), 引数の式, 参照先の計算行すべての call_hash )
  • body_hash：関数本体の構文木から位置情報を除いて正規化したもののハッシュ。空白やコメントの変更では変わらない。構文解析は対象プロジェクトの REPL セッションで行う（P10）。本体が使っているモジュール属性の定義と、モジュール冒頭の use・import・alias・require を含める。
  • 自己再帰：自分自身への呼び出しはハッシュの計算から除く（本体は body_hash に含まれている）。
  • 相互再帰：呼び出しグラフの強連結成分を1単位とし、成分内の本体ハッシュをまとめてハッシュする。成分内の関数は同じ dep_hash を持ち、hash_status = cyclic とする。
  • 取りこぼし：動的呼び出しや変数で渡された関数の呼び出しを含む関数は hash_status = incomplete とする。その関数の計算行は、ハッシュが同じでも stale の可能性があるものとしてテーブルに示す。trace 表で実際の呼び出しを確認できる。
  • プロジェクト外の関数：標準ライブラリや依存ライブラリの中身はハッシュしない。実行環境の側（9.3節）で扱う。
  • 提供元による差：提供元によって呼び出し先が食い違う場合は、突き合わせ検査（11.6節）の不一致として needs_review にする。

9.3 実行環境

実行環境の版は、ハッシュではなく git で扱う。

  • 評価時に、コミットのハッシュ、コミット日時、dirty（未コミットの変更の有無）を計算行に記録する。同一性の判定にはコミットのハッシュを使い、日時は表示と並べ替えに使う。
  • 再スキャン時に、記録したコミットと現在のコミットの間でロックファイルが変わったかを調べる（git diff --name-only <記録> HEAD -- <ロックファイル>）。変わっていれば stale とする。
  • どのファイルをロックファイルとみなすかは、REPLアダプタと境界規則が宣言する（Elixir なら mix.lock、Rustler なら Cargo.lock、Nix なら flake.lock）。
  • dirty で評価した結果は、stale の可能性があるものとしてテーブルに示す。
  • 対象プロジェクトは git で管理されていることを前提とする。

11. 解析の提供元

11.1 主経路と基本動作

関数の一覧、接続関係、名前変更は、言語サーバー（LSP）の標準要求を主経路とする。構文解析は、LSP が返さない判定式と、ディスク上にないセルの式に限る。

11.2 機能ごとの判定

言語サーバーは接続時に対応機能の一覧（capabilities）を返す。Xipe Totec は、この一覧を見て機能ごとに LSP と基本動作を振り分ける。言語サーバーの機能が増えれば、設定を変えずに LSP 側へ移る。どちらの経路で得た結果かはスキャン記録に残す。

Elixir の既定の言語サーバーは Expert とする。動作確認済みの版は配布時に添え書きする。

11.3 優先順位

機能ごとに、次の順で使える提供元を選ぶ。使えない、応答しない、検査に失敗した場合は次に回す。

  1. クライアント提供：クライアント側で動いている言語サーバー（ブラウザ側の言語サーバーを含む）や構文解析に、クライアントが問い合わせて中継する。
  2. 利用者が構成した多重化プロキシ：1つの言語サーバーを複数のクライアントで共有する仕組み（rust-analyzer 向けの lspmux など）。
  3. 自前起動：Xipe Totec が起動した言語サーバー。
  4. 基本動作：11.1節の表。

11.4 要求の形

  1. 能力の宣言：接続時に、クライアントは提供できる機能を宣言する（対応言語、言語サーバーの名前と版、文法の版）。
  2. 要求：Xipe Totec はクライアントに provider/* を送る。要求には対象ファイルのパスと、ディスク上の内容の content_hash を含める。
  3. 応答：クライアントは、解析した内容の content_hash を付けて結果を返す。
  4. 照合：応答の content_hash がディスク上の内容と一致しなければ、結果を破棄して次の提供元に回す。未保存のバッファを解析した結果はこれにより破棄される。編集中の内容は、保存時にカードへ反映される。
  5. 時間切れ：応答を待つ時間はパラメータとする（第17章）。起動直後の索引作成中は参照検索だけが遅くなりうるため、要求の種類ごとに分ける。

11.5 受け入れ検査

  • 提供元ごとに、初回はREPLアダプタの検査用ソースで結果を検査し、provider テーブルに記録する。
  • 検査結果は、提供元の版を表す値の組（言語サーバーの名前と版、capabilities、文法の版、REPLアダプタの版と検査用ソースのハッシュ、ロックファイル）と一緒に記録する。
  • 接続時や再スキャン時に組が変わっていれば、自動で検査をやり直す。利用者が明示的にやり直すこともできる。

11.6 突き合わせ検査

LSP の結果と構文解析の結果は別の経路から来るため、突き合わせて整合を確かめる。節ごとの送信先（link.clause）は、LSP が返す呼び出し位置を、構文解析で得た節の本体範囲に当てはめて決める。

検査 不一致なら分かること
ガードの変数が、同じ節の頭で束縛されているか ガードの切り出し位置がずれている、または節の境界を取り違えている
節の頭の引数の数が、node の arity と一致するか 関数と節の対応がずれている
LSP の呼び出し位置が、いずれかの節の本体範囲に入るか 節の範囲が途切れている、または結果が古い
ガードや節の範囲が、LSP の関数の範囲に収まるか 両者が別の版のソースを見ている
構文解析で見つけた呼び出しと、LSP の送信先の数が合うか 動的呼び出しや、解決できなかった呼び出しがある

不一致があった関数は needs_review とし、どの検査で外れたかを診断として返す。

11.7 1バッファ1サーバーのクライアント

名前解決は、クライアント側が既存の言語サーバーに問い合わせて結果を中継する形をとるため、1つのバッファに1つの言語サーバーしか割り当てられないクライアントでも、Xipe Totec を言語サーバーとして並べて登録する必要はない。LSP モード（16.4節）は、中継の仕組みを持たないクライアント向けの任意の入口とする。

11.8 ビルドの取り合い

言語サーバーと REPL が同じプロジェクトを同時にビルドすると、ビルド成果物を壊すことがある。Expert はビルドを専用の場所で行うため、既定では REPL は通常のビルド先を使う。他の言語サーバーと併用する場合に備え、REPL 側のビルド先を分けるパラメータ（repl.build_root）を用意する。

ロックファイルの宣言 9.3節で使うファイルの一覧
トレースの手段 関数の呼び出し・戻りを観測する方法
出力形式 計算行を言語標準のテスト形式（doctest 等）に変換する
検査用ソース 受け入れ検査に使う小さなソース群と期待結果

12.3 受け入れ検査

REPLアダプタは、採用前に以下の検査に合格しなければならない（P4）。

  1. 同じ計算行群を2回評価し、正規形が完全に一致すること。
  2. exact と判定した正規形を REPL に再入力して評価した結果が、元の正規形と一致すること（往復検査）。
  3. 構文解析が、検査用ソースに対して期待どおりの節とガードを返すこと。
  4. 書き換え規則が、検査用ソースに対する名前変更で、期待どおりの修正リストを返すこと。

12.4 正規化の注意点

REPL の表示文字列は、比較用の正規形とは限らない。REPLアダプタは少なくとも、マップ・集合のキー順序、浮動小数点の桁と表記、表示が省略される値、関数値や参照など表示できない値、プロセスIDなど実行ごとに変化する値を扱い、repr を正しく判定する必要がある。

12.5 名前空間規則

言語 ファイルとモジュールの関係 ファイル名変更時の扱い
Elixir 対応は慣習のみ。1ファイルに複数モジュールを置ける 慣習に沿ったモジュール名の変更を diff に含めて提案する
Haskell モジュール名とパスの一致が事実上必須 モジュール名と連動して変更する
OCaml ファイル名がそのまま最上位のモジュール名 モジュール名と連動して変更する
Clojure 名前空間とパスの一致が読み込みに必要 名前空間と連動して変更する
Racket ファイルがモジュールであり、参照がパスで書かれる パスによる参照を書き換える

12.6 初期対象と候補

初期対象は Elixir とする。以降の候補として、Haskell（GHCi / doctest）、OCaml（utop / mdx）、Clojure（REPL）、Racket（REPL / rackunit）などを想定する。

13. 境界規則

13.1 位置づけ

Elixir から Rust などの他言語の関数を呼ぶ構成では、他言語の関数は Elixir 側のスタブ関数として呼べる。このため、計算行の評価は窓口側の言語（Elixir）のREPLアダプタだけで行える。境界規則は、両側の言語のREPLアダプタを前提に、その間の対応だけを担う独立した部品とする。境界の種類ごとに追加・削除でき、既存のREPLアダプタに手を入れる必要はない。

13.2 必須機能（Rustler の場合）

機能 内容
境界の検出 Elixir 側の use Rustler モジュールと、Rust 側の rustler::init! の組を見つける
名前の対応 スタブ関数と #[rustler::nif] 関数を結ぶ（name 属性を考慮する）
リンク行 境界をまたぐリンクを張る
型 両側の型情報（@spec と Rust のシグネチャ）を併記する
書き換え規則 名前変更時に、スタブの定義、Rust の関数名または name 属性、Elixir 側の呼び出し元をまとめて書き換える
依存の伝播 Rust 側のソースの変更をスタブ関数の dep_hash に反映する
ロックファイルの宣言 Cargo.lock
評価への影響 境界の先の依存が変わったら、再評価の前に REPL セッションを再起動するよう Evaluator に伝える
副作用の既定値 境界の先の関数は、解析できるまで effect = unknown とする
トレースの範囲 境界の先を記録できない場合、スタブ関数の trace_coverage を partial とする

13.3 補足

  • Rust 側のファイルもシートとして登録する。NIF として公開されていない Rust 内部の関数は、Elixir から評価できないため、リンク行だけのカードになる。
  • 環境を Nix で固定している場合、境界の先が変わるのはソースやロックファイルを更新してビルドし直したときに限られる。これは 9.2節と 9.3節の仕組みで検出される。セッションの再起動で失われた束縛は lost として示される。
  • 同じ枠組みで、Zigler（Zig）、Port による外部プロセス、Erlang モジュールなどの境界を扱える。

14. 処理フロー

14.1 スキャン

  1. 指定ディレクトリ配下のファイルを、パスと内容ハッシュで sheet に登録する（ファイルはコピーしない）。
  2. 提供元（第11章）を通じて、関数の一覧と範囲を得る。階層コードを振る。
  3. 対象プロジェクトの REPL で、節・ガードを構文解析する。
  4. 提供元を通じて参照を解決し、境界規則の対応を加えて link を確定する。
  5. 突き合わせ検査を行う。
  6. 既存の関数とのID照合を行い、墓標・要確認を更新する。
  7. body_hash、dep_hash、hash_status、effect（inferred のもの）を更新する。ロックファイルの差分を調べ、stale を更新する。
  8. ぶら下がり参照を検出し、診断として記録する。
  9. 常駐時はファイル監視により、変更のあったファイルのみ差分で再スキャンする。

14.2 評価と再計算

  1. 引数セルの編集、または評価要求を受け取る。
  2. 参照を解決し、依存順を決める。対象を 6.6節の規則で絞る。
  3. 境界規則から再起動の指示があれば、REPL セッションを再起動する。
  4. 各計算行を 6.4節の手順で評価する。安全装置（6.7節）を適用する。
  5. 更新された計算行を参照している下流の計算行を、同じ手順で再計算する。
  6. 変更のあった行ごとに、購読しているクライアントへ通知する。

14.3 連動修正

関数名セルまたはシート名（ファイル名）を編集したとき、その変更を対象プロジェクトのソースに反映する。

  1. クライアントからの編集を編集イベントとして受け取る。
  2. 「現在のブック＋編集イベント → 修正リスト」を計算する。LSP の rename・willRenameFiles が使えればその結果を、使えなければREPLアダプタと境界規則の書き換え規則を用いる。修正リストには、定義側と参照側の両方の書き換えを含む。
  3. 修正リストを diff としてクライアントに返す（プレビュー）。
  4. 承認後に適用する。
  5. 再スキャンし、ぶら下がり参照がないことを確認する。
  6. 影響を受けた計算行を再計算する。

取り消しは、逆の編集イベントの適用として扱う。ディスク上のファイルを書き換えた後、エディタ側のバッファを読み直すのはクライアントの責務とする。

Elixir で関数名を変更したときの書き換え箇所

箇所 自動修正
定義側：複数節の def すべて、@spec、@doc 内の doctest 可
呼び出し：完全修飾、alias 経由、import 後の修飾なし呼び出し 可
import の only: / except: の中 可
関数キャプチャ（&Mod.f/2）、defdelegate 可
behaviour の @callback と、それを実装する他モジュールの def 可（実装側をすべて同時に変更する）
apply/3 のアトム、文字列、設定ファイル 不可（needs_review）

同名で引数の数が違う関数は、別の関数として書き換えの対象から外す。引数の数が変わる変更はシグネチャ変更であり、自動修正の対象外とする。

Elixir でファイル名を変更したとき

Elixir ではファイル名とモジュール名が言語上連動しないため、慣習に沿ったモジュール名の変更と、それに伴う参照側の書き換えを diff に含めて提案する。

箇所 自動修正
defmodule の名前、入れ子モジュールの接頭辞 可
完全修飾の呼び出し、alias / import / require / use 可
alias 経由の短縮呼び出し 条件付き（末尾の名前が変わる場合のみ。as: 指定なら不変）
構造体 %Mod{}、型 Mod.t()、@behaviour、defdelegate ... to: 可
関数キャプチャ、@doc 内の doctest 可
設定ファイル中のアトム、Module.concat、文字列 不可（needs_review）
  • 1ファイルに複数モジュールがある場合は、パスの慣習に対応するモジュールだけを改名対象とする。
  • 対応するテストファイル（test/shop/price_test.exs と Shop.PriceTest）の改名も提案する。
  • 移動先に同名ファイルがある場合は、自動で決めず衝突として提示する。

14.4 自動修正しない対象

動的呼び出し、マクロ展開後にのみ現れる参照、文字列や設定ファイルに書かれた名前は、静的に追跡できない。これらは自動修正の対象から外し、needs_review として提示する。LLM による修正候補の提示は許容するが、適用は利用者の承認と 14.3節の確認を経る。

14.5 記録と取り込み

  1. 記録開始の要求を受け、run を発行し、対象プロジェクトの REPL にトレースを設定する。
  2. 呼び出し・戻りのイベントを trace に追記する。戻りの時点で、飛ばされた送信先の no_data 行を追記する（設定で無効にできる）。
  3. 行数の上限に達するか、記録終了の要求を受けたら、トレースを解除する。
  4. 取り込み要求に応じて、選ばれた observed 行を call に追加し、評価する。

19. 非機能要件と配布

19.1 非機能要件

  • 再現性：同一のソース、同一のコミット、同一の設定（提供元の構成を含む）から、同一のカードと同一の修正リストが得られること。IDの新規付与と trace の記録内容は例外とする。
  • ローカル完結：既定で外部ネットワークに接続しない。LLM との連携は、外部の LLM 系ツールが MCP 経由で Xipe Totec を呼ぶ形とする。
  • 単体動作：クライアントや言語サーバーの提供がなくても、基本動作だけで全機能が動作すること。
  • 実行環境の分離：Xipe Totec 自身の実行環境は、対象プロジェクトの言語のバージョンに依存しないこと。
  • 性能：常駐時の差分再スキャンと、単一の引数セル編集に伴う再計算が、対話的な応答時間に収まること。

19.2 配布

  • GitHub で公開し、Nix flake から提供する。Erlang/Elixir の版と、既定の言語サーバーの版を flake で固定する。開発用の devShell も同じ flake で提供する。
  • 版が明らかなため、後に mix release、escript（Hex 経由）、Burrito による単体バイナリへ広げる。Hex のパッケージ名は公開時に確認する。

19.3 配布時の注釈

  • 対象プロジェクトは git で管理されている必要がある。
  • 使用する言語の REPL が、対象プロジェクトの環境で使える状態になっている必要がある。
  • 評価はサンドボックス化されない。副作用の判定を誤れば書き込みは実際に起こるため、全体の再計算の前にコミットしておくことを推奨する。
  • 言語サーバーの対応機能は版によって異なる。動作確認済みの版を記載する。

22. 先行例と差分

先行例 共通点 Xipe Totec との差
表計算ソフト 住所、参照、再計算、名前変更の追従 対象はセルではなくソースコードであり、変更をソースに書き戻す
リレーショナルデータベース キーによる結合、外部キー制約、ビュー、実体化ビュー 非正規化されたコピーであるソースファイルへ、自然キーの変更を伝播させる
Nix、Bazel 入力のハッシュによる結果の再利用 対象は関数の呼び出し結果
Babylonian-style Programming（HPI） 関数の具体例をコードの横に置く 研究用の専用環境向け。具体例同士の参照は弱い
Glamorous Toolkit（Pharo） 開発中に対象ごとの見え方を作る Smalltalk 環境内で完結
tree-sitter 系 MCP サーバー群 構文解析による呼び出しグラフ 読み取り専用。値の層と書き戻しがない
LSP の rename 参照追跡による名前変更 値の評価とは無関係
Unison 実体をハッシュで識別し、名前はラベル 言語そのものの設計であり、既存言語には適用できない
Hoogle 型による関数の逆引き Haskell 専用の検索
doctest / mdx、スナップショットテスト 対話記録や出力の記録をテストにする 記録同士の参照やグラフとの連動がない
BEAM のトレース（dbg、recon_trace 等） 実行時の関数呼び出しの観測 観測結果を表として保存し、計算行に取り込む

Xipe Totec の独自性は、これらを「テーブルを根とし表計算の見え方を持つ構造として、関数型言語向けに、言語非依存のローカルサーバーとして」1つにまとめる点にある。

ID 決定
U1 名称は Xipe Totec
U2 リンク行は静的構造とし、三つ組はセルに分解する。意味上の対応は節ごとの「判定式と送信先」に限る
U3 保存形式は JSON Lines とし、各行をテーブルの1行として扱う
U4 ID照合は、初回に振って固定する階層ごとの2桁コードと body_hash、名前を手がかりにする。ULID が同一性の本体
U5 実行時観測は、動作順の trace 表として記録し、observed 行を計算行に取り込む
U6 名前解決は基本動作を持ち、機能ごとにクライアント提供・多重化プロキシ・自前起動・基本動作の順で選ぶ。1バッファ1サーバーのクライアントには中継で対応する
U7 配布は GitHub と Nix flake から始める。Xipe Totec と対象プロジェクトの実行環境を分ける
U8 構文解析は判定式とセルの式に限り、対象プロジェクトの REPL で行う。tree-sitter は任意の共通経路とする
U9 Elixir の既定の言語サーバーは Expert。capabilities で機能ごとに判定し、基本動作を実用の経路として作る
U10 副作用は pure / reads / writes / unknown の4区分。自動判定は提案とし、利用者がテーブルで更新する
U11 依存込みハッシュはソースのみを対象とし、実行環境は git のコミットとロックファイルの差分で判定する。相互再帰は強連結成分で扱い、hash_status で完全性を示す
U12 住所は列の組とし、区切り文字を使わない。セル内の参照は計算行の ID のみ
U13 計算行は結果・前回（評価ごとに上書き、期待値としても使える）・比較・評価回数の列を持つ。時間・メモリの上限と、再計算内の評価回数の上限を設ける

U15 評価は止めず、repr（exact / binary / unsupported）で忠実度を示す。外部項形式での保存を認める。state に lost を加える
U16 trace の記録量と保持期間はパラメータとして利用者に委ねる
U17 提供元の時間切れはパラメータとし、受け入れ検査は提供元の版の変化で自動的にやり直す
