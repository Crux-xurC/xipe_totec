# 拡張の手引き

**この文書が答える問い**: xipe_totec に言語やコマンドを足したい人（と、その人が一緒に作業する AI）は、
何を参考に、どういう動作を満たすように作ればよいか。

xipe_totec は関数型言語のプロジェクト向けの管理ツールであると同時に、言語やコマンドを各自が乗せられる土台でもある。
この文書は、2026-09-27 に OCaml と Haskell を足したとき（`Old.md` §42〜§47）に実際に踏んだ手順を型紙にしている。
書いてあることは、その時点のコードで確かめたもの。食い違いを見つけたら、コードを正として直すこと。

---

## 0. AI と一緒に作業する人へ

AI に作業を頼むときは、まずこの文書と `CLAUDE.md` を読ませる。とくに次の3つを守らせる。

1. **実装の前に、実機の REPL で裏取りする**（§2.2）。REPL の性質は、知識で書くと外れる。OCaml では
   「コンパイラ部品を読むと型エラーが人の読める文にならない」、Haskell では「`-fdefer-type-errors` が `let` の束縛に
   しか効かない」が、裏取りで初めて分かった。どちらも、知識どおりに書いていたら動かなかった
2. **実環境に触れない**。xipe_totec は自分の状態（`tables/`・`info.json`）を `__DIR__` 基準で持つので、試すときは
   作業用ディレクトリへ写してから動かす（`CLAUDE.md`「実際に動かして確かめるとき」）。embody は
   `XIPE_TOTEC_EMBODY_DIR` で渡す
3. **決めたことを残す**。仕様の穴を実装で埋めたら（「省略時は `id`」など）、`Old.md` の末尾に節を足して、何を
   確かめ、何を決め、何が残っているかを書く。commit と push は、頼まれたときだけ

## 1. 壊してはいけない約束

言語やコマンドを足しても、次は変えない。変える必要が出たら、それは拡張ではなく設計の変更なので、先に相談する。

| 約束 | 中身 | 根拠 |
|---|---|---|
| 評価するのは指定した計算行だけ | 参照している上流・下流を自動では評価しない。Book は時系列の記録 | `Old.md` §36 |
| Book は追記だけ | `Store.persist_diff/4` が差分を `book.jsonl` に足す。書き換えはしない | `lib/store.exs` |
| 副作用の分類を信用するのは利用者の明示だけ | `effect/set` されていない関数は評価しない。`writes` は `--include-writes` のときだけ | README の P1 |
| 出力の約束 | `XT_BEGIN_<id>` … `XT_END_<id>` の間に `repr=`・`type=`・`compare=`・`display=`、または `XT_ERROR_<id> timeout` / `crash <1行>`。言語で変えない | `~/my_app/embody/ReadMe.md` |
| `repr` の3語彙 | `exact`（そのソースを評価すると元の値に戻る）・`binary`・`unsupported`。`Core` が読む（`⟦id⟧` への埋め込み、前回値との比較）ので、意味を言語ごとに変えない | `Old.md` §30.1 |
| 読み込みで対象の副作用を走らせない | スクリプトのトップレベル、`main` など | `Old.md` §14.1・§42・§45 |
| 評価中にネットへ出ない | ローカルホストだけ。ビルドツールにも `--offline` などを付ける | 仕様 §16.1、`Old.md` §47 |
| 人向けの文字列は、tezcatl が解釈しない | tezcatl は `input` で1行を送り、返事の `dialogue.text` をそのまま見せる | tezcatl `D-xipe対話窓` |

## 2. 言語を足す

### 2.1 足す部品

| 部品 | 置き場所 | 求める動作 | 手本 |
|---|---|---|---|
| 言語の申告 | `lib/repl/language/<言語名>.exs`（ファイル名が言語名。`Repl.Language` の behaviour） | `extensions/0`・`repl/0`・`build_tools/0`・`scanner/0`・`adapter/0`・`launch_opts/3`（`{起動の指定, 後始末}`） | `ocaml.exs`・`haskell.exs` |
| launch | `lib/repl/<言語>/launch.exs` | `build/1` が JSON にできるメッセージを返す: `argv`・`env`・`cwd`・`files`・`ready_pattern`（バナー、無ければ `nil`）・`ready_probe`（`XT_READY` を印字させる入力。マーカーの文字列を分けて書き、入力の反響と区別できるようにする）・`exit_input`・`interruptible` | `ocaml/launch.exs` |
| eval_template | `lib/repl/<言語>/eval_template.exs` | `build(entry)` が1件分の入力テキストを返す。`entry` は `call_id`・`module`・`name`・`args`（参照は解決済み）・`limits`（`timeout` ミリ秒・`max_heap_words`）・`basis`（`{:exact, 前回値}` など）。束縛する変数名は `xt_` ＋ `call_id`（英数字と `_` 以外は `_`、`Core` の `binding_name/1` と同じ） | `ocaml/eval_template.exs` |
| Eval.Scan | `lib/repl/eval/scan/<transport>/<REPL名>.exs` | `clean/1` が出力から `XT_EXIT` の行を取り除く。pipe 接続なら iex 版に委譲するだけでよい | `scan/direct/ocaml.exs` |
| FieldDrip | `lib/repl/eval/field_drip/<言語>.exs` | 本文の `キー=値` を読む。出力の約束に従っていれば Elixir 版に委譲するだけでよい | `field_drip/ocaml.exs` |
| Scanner | `lib/scanner/<言語>.exs`（`XipeTotec.Scanner` の behaviour） | `scan_defs/3`（定義 → ノード）と `scan_links_report/3`（呼び出し関係）。§2.5 | `scanner/ocaml.exs` |
| embody | 別リポジトリ `~/my_app/embody/embody.<拡張子>` | 1件を必ず出力の約束の形で返す。§2.4 | `embody.ml`・`embody.hs` |
| 対象の環境の取り出し方（言語ではなくプロジェクトの層。Nix 以外の道具を足すときも） | `project_env.json` に1行（`marker`・`command`・`format` の `env` か `nix`、要れば `watch`）。tezcatl の `project_env.json` と同じ書き方を保つ。それ以外の道具は `env` 形式（`{"名前": "値" \| null}`）を出すスクリプトを書く | 対象の直下で走り、JSON だけを出す。失敗は終了コードと標準エラー | `How_to_use.md` §4.3、`test/project_env_test.exs` |

`Repl.Language` の各コールバックの意味は `lib/repl/language.exs` の moduledoc にある。4つの部品の組
（launch・eval_template・Eval.Scan・FieldDrip）は、`Runner` が surface table の言語から選んで `Repl.Evaluator` に
渡す。`Evaluator`・`Session`・`Core` は言語を知らないので、触らない。

### 2.2 実装の前に: REPL の裏取り

作業用ディレクトリに、確かめたい性質を集めた小さな対象（トップレベルに副作用のあるファイル、export されない関数、
無限の構造、表示できない値、割り当てをしないループ、例外を投げる関数）を置き、REPL を pipe でつないで確かめる。
Python の `subprocess` か、xipe_totec の `Repl.Sender.Direct` で書き込み・読み出しをする。確かめること:

| 項目 | 何を見るか | OCaml | Haskell |
|---|---|---|---|
| 起動 | pipe 越しにバナーやプロンプトが出るか。`ready_probe` の出力が `flush` なしで届くか | `ocaml -init <file>`、プロンプト `# ` は出る（無害） | `ghci -v0` で何も出ない |
| 読み込み | 対象のファイルを、トップレベルの副作用を走らせずに読めるか。依存の順 | 副作用を空白で塗った写しを `mod_use`、失敗したら読み直す | ファイルを `:load` するだけ（`main` は走らない） |
| 評価と表示 | 型と値を1行の文字列で取れるか。読み戻しの判定ができるか | `Toploop.use_input` の表示 `val x : 型 = 値`、再評価して `=` | `Read`・`Show`・`Typeable`。インスタンスの有無は `let` の中で実行時まで遅らせる |
| 失敗 | 例外・型エラー・構文エラーが、入力待ちで止まらず1行で返るか | 呼び出しを文字列で渡すので、閉じていない引数でも止まらない | 構文エラーは `Variable not in scope` として返る |
| 時間の上限 | 無限ループ（割り当ての無いものも）が止まるか | `Unix.setitimer`（SIGALRM） | `System.Timeout.timeout` |
| SIGINT | 評価だけが止まり、REPL が読み続けるか（`interruptible`） | `Interrupted.` | `Interrupted.` |

裏取りで分かったことは、この表を埋める形で `Old.md` に残す（例: §38.2・§45）。

### 2.3 求める動作（評価）

`Repl.Evaluator` は1件ごとに「書き込む → マーカーを待つ」を繰り返し、締切（`timeout` ＋ 2秒、既定で計7秒）を過ぎたら
REPL が固まったとみなして、SIGINT、効かなければ SIGKILL で落とし、残りを `aborted` にする。したがって:

- **どの行も、締切までに必ずマーカーで終わること**。型エラー・構文エラー・インスタンスの欠け・例外・無限ループの
  どれでも。REPL が続きの入力を待つ状態（閉じていない括弧など）に入ると、その行も後ろの行も失われる。OCaml は呼び出しを
  文字列で渡し、Haskell は `let` で束縛してから実行の行を送ることで、これを防いでいる
- **1件の結果は1回の書き込みで印字すること**。ほかの出力が間に割り込むと読めなくなる
- **同じ回の後の行から、前の結果を `xt_<id>` で参照できること**。`Core` は同じ回に評価する参照先を変数名で埋め込む
- **引数は括弧で包むこと**。`-1` や `Some 2` のような埋め込まれた値が、式の結合を変えないように
- `compare` は前回値（`exact` のとき）を評価して比べる。`binary` の前回値を扱えない言語では、比較しない（`none`）
- メモリの上限を持てない言語は、持たなくてよい（固まれば REPL ごと落とす経路がある）。OCaml・Haskell は持っていない
- **起動の待ち時間は15秒**（`Evaluator` の既定値 `@default_boot_timeout_ms`、言語から変える口はまだ無い）。起動の前に
  ビルドする構成（dune・cabal）では、初回のビルドがこれを超えると起動に失敗する（`課題.md` §3）

### 2.4 embody を書く

embody は、対象を知らない固定のモジュール。REPL に読み込まれ、呼び出し側が送る1行（または数行）を受けて、出力の約束の
形で印字する。`~/my_app/embody/ReadMe.md` に共通の約束と各言語の中身がある。書くときの要点:

- **対象に依存しない**。どの関数を評価するかはテキストで届く。解釈は REPL 自身（OCaml の `Toploop`、GHCi）に任せる。
  コンパイル時に対象へ依存させる形は、対象ごとに作り直しが要るので成り立たない（`Old.md` §30.2）
- **言語の標準の範囲だけで書く**（OCaml はトップレベル自身＋`unix`、Haskell は `base`）。外部パッケージに依存すると、
  対象の環境にそれが無いときに読み込めない
- 表示しきれない値（無限の構造、関数、循環）も、有限の表示と `repr=unsupported` で返す。読み戻せる値だけを `exact` にする
- embody を足したら、`embody/ReadMe.md` の「ファイル」の表と言語の節を書き、embody のリポジトリに commit する
  （xipe_totec とは別のリポジトリ。xipe_totec は `lib/repl/embody.exs` で置き場所を探す）

言語によっては embody がほぼ要らない（往復検査を標準で持つ Racket など、`Old.md` §30.6）。その場合も、出力の約束を
組み立てる部分はどこかに要る（Elixir は `lib/repl/eval_template.exs` がその役を持っている）。

### 2.5 Scanner を書く

Scanner は、ファイルから定義（カードになる関数）と呼び出し関係（リンク）を取る。

- **定義**: `%{module:, name:, anykey:, visibility:, span:, body_hash:}`。`(module, name, anykey)` が自然キーで、
  再スキャンのたびに同じ関数は同じ id を引き継ぐ。`anykey` は同じモジュールの同名の関数を区別する値
  （Elixir は arity。カリー化する言語は `nil`）。整数なら引数の数としても使われる（`row/add` が確かめる）。
  `visibility` は REPL から呼べるかどうか（`private` だと `row/add` が拒む）
- **呼び出し関係**: 求められているのは、ファイルの中の関数どうしの依存が分かること（crux、`Old.md` §42.4）。
  OCaml・Haskell は、コメントと文字列を塗りつぶしたテキストから推定している。コンパイラや言語サーバーから正確に取れる
  言語ならそれでもよい（Elixir はコンパイラのトレーサー、`Scanner.Lsp` は `callHierarchy`）。言語サーバーを使う場合は
  `Scanner.Lsp` の上に薄い dialect を書く（`scanner/lsp/elixir.exs`）。ただし `callHierarchy` の無いサーバー（ocamllsp）
  では呼び出し関係が取れない
- 使う Scanner は `scanner/0` で申告する（複数なら優先順。最初に `begin/3` が受け入れたもの）

### 2.6 ビルドツール

ビルドツールは REPL を変えず、起動の仕方だけを変える（next_step §2.3）。`build_tools/0` で目印のファイル
（`dune-project`、`*.cabal` など）を申告すると、`xipe table generate` が surface table の `build_tool` 列に入れ、
`launch_opts/3` の第2引数に届く。

| 言語 | ビルドツール | 起動の変え方 |
|---|---|---|
| Elixir | mix | `iex -S mix` |
| OCaml | dune | 依存ライブラリを `dune ocaml top` から読む（自身の `.cma` の行は除く）。包まれたライブラリの別名を作る（§43） |
| Haskell | cabal・stack | `cabal exec --offline --`（その前に `cabal build --offline all`）・`stack exec --` の下で `ghci` を起動する（§47） |

どの場合も、プロジェクト自身のコードは xipe がソースから（副作用なしで）読む。ビルドツールの REPL（`cabal repl` など）に
全部を任せる形は、embody を足せない・コンポーネントを一度に読めない、といった理由で採っていない（§47.1）。

### 2.7 登録・テスト・記録

1. `xipe refresh -a`（`lib/repl/language/*.exs` と `lib/repl/eval/scan/<transport>/*.exs` を読み、`info.json` に書く）。
   ファイルを置いただけでは使われない（P4）
2. `test/info_test.exs` の、登録される言語・REPL の一覧の期待値を更新する
3. 単体テスト `test/<言語>_adapter_test.exs`（処理系が無くても走る）: テンプレートの形、起動の指定、Scanner の定義と
   呼び出し関係。`./test/run.sh` に入る
4. 実機テスト `test/live/repl_<言語>_test.exs`: 処理系が PATH に無ければ除外する（`ExUnit.start(exclude: …)`）。
   値と型・参照・失敗（例外・型エラー・構文エラー・時間切れ）・前回値との比較・読み込みで副作用が走らないこと・SIGINT。
   対象に書き込むもの（`_build/` など）がある場合は、fixture を一時ディレクトリに写してから動かす
5. fixture `test/fixtures/<言語>_sample/`。**リポジトリの `.` を評価の対象にするテストに注意**: fixture を足すと
   xipe_totec 自身の言語が増え、`runner_test` の「ファイルを持たない行」の言語が決まらなくなる（`language:` を明示して
   避けている）
6. 作業用の写しで CLI を通す: `choice project` → `table generate` → `scan` → `do row/add … -- eval` → もう一度 `eval`
   （`compare=same`）
7. 文書: `Old.md` に節を足す。How_to_use §9 に言語の節、README の「いまどこまで動くか」、`課題.md` の残り

## 3. コマンドを足す

### 3.0 足す前に: 足してよいものの基準

Xipe Totec は、言語サーバーや REPL など**対象の環境を使う部分を集めたもの**（crux、2026-10-11）。取ってきたものを見るのは
個々の道具（CLI、tezcatl の表）の仕事で、SQL のような問い合わせのコマンドを増やさない。ただし、毎回本格的な環境を開かなくても
簡単に見ることは出来てよい。README の P7（入力体験はクライアントの責務）・P9（状態は列として示す）と同じ向き。

足してよいのは次の4つ。

1. **対象の環境を使うもの**（REPL・言語サーバー・ビルド）
2. **Book を書くもの**（整合性を見るのは Xipe Totec だけ）
3. **丸ごと返す読み出し**（id の並びで選ぶところまで）。**新しい情報は、コマンドでなく列で足す**（`row/list` の列など）
4. **簡単に見るための最低限**。今あるもの（`show`・`search`・`eval/status`）で足りているかを先に見て、足りなければ CLI の側に足す
   （method は増やさない）

絞る・並べる・辿る・形を変えるは、受け取った側の仕事（tezcatl の表の絞り込みと並べ替え、端末なら `jq`・`grep`）。
今ある問い合わせの method（`card/get`・`card/search`・`node/resolve`・`row/depends`・`row/check`・`graph/*`）は消さないが、
これ以上は増やさない。`search` も同じで、ターンの種類は増やさない。**表と列は足してよい**（crux、2026-10-12）── 分かりやすい形で
情報を渡すのは Xipe Totec の役目で、丸ごと返す読み出し（3）と `search`（4）が同じ表を使う。個々の案の扱いは `document/scope.md` の「予定」と `../tezcatl/document/コマンドの案.md` §2。

### 3.1 どこに足すか

| 種類 | 足す場所 | 自動で付いてくるもの |
|---|---|---|
| Book を読むだけ | `Dispatch.handle/4` に節を1つ ＋ `Methods` に `route: :dispatch, writes: false` | CLI（`xipe do`）・WebSocket・対話窓（method 名から始まる行）の全部。`help` の一覧 |
| Book を書き換える（REPL を使わない） | 同上、`writes: true` | 同上。サーバーでは `notify/rowChanged` の配信、セッション中の CLI の警告 |
| REPL を使う組み合わせ | `pipelines.json` に段を並べる（新しい段は `Pipeline` の `stage_handlers/0`）＋ `Methods` に `route: :pipeline, repl: true` | CLI は同期。サーバーは `"eval"` より前の段をその場で、`"eval"` を評価回の順番待ちで |
| 複数ターンの対話 | `lib/dialogue/<名前>.exs`（`Dialogue` の behaviour）＋ `InOut.programs/0` に登録 | CLI（入口は自分で書く）・WebSocket・対話窓 |
| 見るための表・手で書き換えられる列 | `lib/tables.exs` の `all/0` に表を1つ（名前・印・列・行の読み方）、または `writes` に列を1行（その列を書く method） | `search` のターン・`roster`・`dialogue rewrite`（値の尋ね方はその method の `params` から） |
| プロジェクトごとの設定 | `lib/project_config.exs` の `@keys`（選択肢か、範囲つきの数）と `@builtin`、`defaults.json` に既定値 | `xipe config`・`config/set`・`dialogue update` の一覧と検査。使う側は `ProjectConfig.load/1` で読む |
| 人に指し示したいファイル | そのファイルを、出す行の括弧の中の最後にパスつきで書く（`(eval.timeout, /…/project.json)`） | `tables/logging_buffer.txt` に残り、`dialogue update` が番号で選ばせる（`.json` だけ） |
| CLI 専用（Book を触らない） | `main.exs` の `main/1` と、`lib/help.exs` の表 | — |

### 3.2 求める動作

- **`Dispatch.handle/4` は純粋**（Book を受け取り Book を返す。I/O は `scan/run` のファイル読みだけ）。
  返すのは `{:ok, book, 結果の map}` か `{:error, book, %{"code" => …, "message" => …}}`。失敗したら Book は変えない
- **params は JSON の形**（文字列のキー）。CLI の `key=value` は `CommandLine` が文字列かリストにして渡す
  （`[..]` は常にリスト、カンマを含む値もリスト）
- **`Methods` の表に必ず載せる**。引数は `params` にデータで宣言する（名前・種類 `:node`/`:call`/`:value`/`:choice`/`:number`/
  `:flag`/`:address`・必須か・リストか）。`help` に出る引数の書き方（`args`）はそこから作られ、`dialogue do` は必須のものを
  その順に尋ねる。`summary`（1行の説明）は `help` にそのまま出て、tezcatl の利用者はそれを辞書に登録して補完に使う。コマンド名に `:` を含めない。`test/methods_test.exs` が、表と `Dispatch` の
  節を両方向から突き合わせ、`test/help_test.exs` が実装済みの method に説明があるかを確かめる
- REPL を使うものは `Dispatch` に入れない（サーバーの GenServer が評価の間止まる）。`Pipeline` の `"eval"` 段を使う
- 対話プログラム: `start`/`answer` が `{:hold, state, text}`・`{:done, text, commands}`・`{:pass, state, line}` の
  どれかを返す。Book を読むなら `start/2`・`answer/3`（読み取り用の `ctx`）。Book を変えるのはコマンドだけ。
  1行の読み方は `parse_answer/1`（無ければ `%{"text" => 行}`）。例: `Dialogue.Depends`・`Dialogue.Search`（`Old.md` §41）・`Dialogue.Do`・`Dialogue.Rewrite`（列を選んだあとは `Dialogue.Do` に渡す
  ── 別の対話の中身を借りる例）。method を1つ実行するだけの対話なら、新しく書く前に `dialogue do` で足りないかを見る

### 3.3 入口

- **CLI**: `xipe do <method> …` で使えるので、専用のサブコマンドは要らないことが多い。作るなら `main.exs` の `main/1` と
  `lib/help.exs` の `@commands`（`window: true` なら対話窓でも使える）
- **対話窓**: 1行の読み方は `lib/input.exs`（CLI と同じ書き方。method 名から始まる行は `do` を省いたもの）。
  CLI のサブコマンドを窓でも使えるようにするなら、ここに節を足す
- **WebSocket**: `Methods` に載っていれば、そのまま使える

### 3.4 テスト・記録

`test/dispatch_test.exs`（または専用のテスト）、`methods_test`・`help_test` が通ること、対話窓から使うなら
`test/serve_input_test.exs`。How_to_use §3.2 の method の表、README の method の表、`Old.md` の節。
