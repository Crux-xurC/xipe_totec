# 動作原理

**この文書が答える問い**: 使う場面ごとに、何がどの順で呼ばれ、そのステップを
担っているのはどのプログラムか。

tezcatl の `draft/doc/02-構造.md`(責務分担+名前付き決定)に相当する文書は
xipe_totec には作らない ── 構造を語るほど部品間の関係が複雑ではなく、むしろ
「どのシーンでも動線がほぼ一本道」という性質の方が特徴的なツールなので、
その動線をシーンごとに書き下す形にした。**言語（対象プロジェクトがElixirか
どうか）による分岐は§11に書く「`Evaluator`へ渡す4モジュールの選択」だけ**で、
それ以外はどのシーンでも同じ順序で同じモジュールを通る（各シーン自身が持つ
別種の分岐点──§3の`"eval"`かどうか、§7のPipeline経由かどうか──とは別軸なので
混同しないこと）。

各ステップの「なぜこの形か」は `work_history/Old.md` の対応する節
(§番号を添えた)を見ること。ここには経緯・代替案は書かない、動作の道筋だけ書く。

---

## 0. 前提として: 全シーン共通の3つの土台

どのシーンも、最終的にはこの3つの上に乗る（`Store`はファイルI/Oを行うので
純粋ではない。純粋なのは`Book`/`Core`の2つだけ）。

| モジュール | ファイル | 役割 |
|---|---|---|
| `XipeTotec.Book` | `lib/book.exs` | 6テーブル(`sheets`/`nodes`/`calls`/`links`/`runs`/`providers`)の in-memory 現在状態。`id => 最新行` のマップの集合 |
| `XipeTotec.Core` | `lib/core.exs` | Book に対する純粋関数(参照グラフ・循環検出・`plan_recalc`・`apply_results` 等)。I/O 一切なし |
| `XipeTotec.Store` | `lib/store.exs` | `book.jsonl` への追記型永続化。`load/1` で Book を再構成、`persist_diff/4` で差分だけ追記（I/Oあり） |

どのCLIサブコマンドも「`Store.load` で古い Book を読む → 何かする → 新しい
Book と差分を `Store.persist_diff` で書く」という形を出ない。

**Book はプロジェクトごと**(2026-09-24、Old.md §31): `book.jsonl`は
`tables/project/<id>_<name>/book.jsonl`にあり、どのファイルを読み書きするかは
各コマンドの冒頭で`XipeTotec.Workspace.resolve/2`が決める(§10)。以下の図の
`"book.jsonl"`はこのプロジェクトごとのファイルを指し、`dir`はそのプロジェクトの
絶対パスを指す。

## 1. シーン: `xipe scan [<dir>]` ── ソースをスキャンして Book に反映する

```
main.exs (XipeTotec.CLI.scan/1)
  → Workspace.resolve(<dir> または nil)                 … §10。未選択・未登録ならここで終了
  → run_commands(project, [%{"method"=>"scan/run","params"=>%{}}])
      1. Store.load("book.jsonl")                         … 旧Book
      2. XipeTotec.Runner.run/4                            … コマンドリストを実行
           → XipeTotec.Dispatch.handle(book,"scan/run",%{},%{root: dir})
               → XipeTotec.Project.scan_dir(book, dir)
                   1. Project.sheets(dir, info, table_file) … XipeTotec.SurfaceTable.rows/3
                        で保存済みの table を読み(無い・載っているパスが消えて
                        いれば作り直して保存)、登録済み言語の行のパスだけを
                        取り出す(相対パス、ソート済み)
                   2. 各ファイルについて1パス目:
                        XipeTotec.Scanner.scan_defs/3        … AST走査のみ(コンパイルしない)
                        → defmodule/def/defp を抽出、(module,name,anykey)の
                          自然キーで既存node idを再利用 or 新規発番
                   3. 全ファイルの1パス目が終わってから2パス目:
                        XipeTotec.Scanner.scan_links/3        … defmoduleフォームだけを
                          Code.compile_quoted/2 でコンパイルし、コンパイラ
                          トレーサー(Scanner.Tracer)で呼び出しエッジを収集
                   4. 消えたnode/linkをtombstone化
      3. Store.persist_diff("book.jsonl", 旧Book, 新Book, 全6テーブル)  … 差分だけ追記
      4. 結果行を標準出力へ
```

**担っているプログラム**: `main.exs` → `Runner` → `Dispatch` → `Project`
(→ `SurfaceTable`) → `Scanner`(AST抽出+コンパイラトレーサー) → `Store`。`Core` はここでは出てこない
(スキャンは参照解決や再計算をしない)。

## 2. シーン: `xipe show` ── 現在の Book を表示するだけ

```
main.exs (XipeTotec.CLI.show/1)
  → Workspace.resolve(<dir> または nil)
  → Store.load("book.jsonl")
  → sheets/nodes/links を1行ずつ IO.puts
```

`Runner`/`Dispatch` を経由しない唯一のサブコマンド ── 何も変更しない読み取り
専用の操作だから(`Runner`が仲介するのは「Bookを変更する/外部プロセスを起動
する」操作であり、`show`はどちらでもない)。

---

## 3. シーン: `xipe do [--dir <dir>] <method> [key=value...] [-- <method> ...]` ── 汎用コマンド列

`xipe scan`/`xipe eval` は実はこの仕組みの上に乗った「1コマンドだけの
コマンドリスト」に過ぎない。`xipe do` はこれを直接使う入口。

```
main.exs (do_cmd/1)
  1. 先頭の "--dir <path>" があれば取り出し、Workspace.resolve で対象プロジェクトを決める
     (無ければ選択中のプロジェクト、§10)
  2. 残りの引数を "--" で分割 → 各グループの先頭語がmethod名、残りが
     "key=value" ペア(XipeTotec.CommandLine。[..]は常にリスト、それ以外もコンマを
     含めばリスト)
     → コマンドリスト [%{"method"=>, "params"=>}, ...] を組み立てる
        (この形は §16.3 の実際のwireメッセージと同じ形 ── XipeTotec.Runner のmoduledoc参照)
  3. run_commands(dir, commands)
      → XipeTotec.Runner.run(book, dir, commands, opts)
          Enum.reduce で先頭から1つずつ:
            a. substitute/2 で "$<番号>.<path>" 参照を、それより前のコマンドの
               結果から解決する(例: "$0.id" → コマンド0の結果の "id" フィールド)
            b. method が "eval" なら → §5 のREPL往復フローへ(Dispatchを経由しない)
               method がそれ以外なら → Dispatch.handle(book, method, params, ctx)
            c. 結果(ok?/result/error)を1件のoutcomeとして蓄積、Bookを次へ渡す
  4. Store.persist_diff で最終Bookとの差分を永続化
  5. 各コマンドのoutcomeを1行ずつ表示
```

**分岐点はここに2つ**:

1. 各コマンドの method 名が `"eval"` かそれ以外かで `Dispatch`(Bookの純粋な
   変換)と `Evaluator`(REPLの生きたI/O)のどちらに渡すかが決まる
2. `"eval"` 以外の method は、さらに `XipeTotec.Pipeline.handles?/1`
   （`pipelines.json`、2026-09-18新設）に登録されているかどうかで
   `Pipeline.run/4` と `Dispatch.handle/4` のどちらへ渡すか決まる。
   現状の登録は`eval/run`（`["eval"]`）・`row/update`（`["edit", "eval"]`）の2つ。
   `"eval"`段はRunner自身の`"eval"`（`ctx.eval`として渡す）で、REPLを使う基本の操作は
   これ1つだけ（2026-09-26、Old.md §37）。サーバーは`"eval"`より前の段をその場で実行し、
   `"eval"`段だけを評価回のキューに回す（`Pipeline.prepare/4`）。登録されていない
   methodは従来どおり`Dispatch.handle/4`へ

それ以外の分岐は無い ── `Dispatch.handle/4` 自体は method 名で
実装済みの節に振り分けるだけの表引きで、`row/add`/`row/remove`/`effect/set`/
`card/get`/`card/search`/`graph/neighbors`/`graph/export`/`cell/resolve`/
`row/depends`/`row/set-result`/`scan/run` はそれぞれ対応する `Core`/
`Project`/`Address`/`GraphQuery` の純粋(または薄いI/O)関数を呼ぶだけで、
未実装のメソッド(`cell/complete`/`edit/*`/`trace/*`/
`provider/recheck`、およびフォールバックとして`row/update`/`eval/run`)は例外を投げずに `not_implemented` エラーを返して終わる
（ただし`eval/run`/`row/update`は上記2.の通り`Pipeline`側で先に横取りされる
ため、`Dispatch`の`not_implemented`はそこに直接到達する呼び出し元向けの
フォールバックとしてのみ残っている）。

## 4. `xipe eval [<dir>] [id...] [--mix] [--include-writes]` は §3 の特殊形

```
main.exs (eval/1)
  → 先頭の引数が既存のディレクトリなら <dir>、そうでなければ全部 call id として扱う
  → Workspace.resolve で対象プロジェクトを決める(§10)
  → target_ids を決める(引数が無ければ Book の全call id)
  → コマンドリスト [%{"method"=>"eval","params"=>%{"call_ids"=>target_ids,
                                                    "include_writes"=>...}}]
  → run_commands(dir, [そのコマンド], ctx: git_ctx(dir))
```

`--include-writes`(2026-09-21)は`params["include_writes"]`にそのまま乗り、
`Runner.run_one/4`の`"eval"`節が読んで`Core.plan_recalc/3`（§6参照）へ渡す。
無指定(既定`false`)だとwrites/unknown effectの計算行は`filter_by_effect/3`で
スケジュールから外れる。

頼まれたのに評価されなかった行(効果が未分類・`writes`で`--include-writes`無し・
循環参照・ノード消失)は、評価の後で`Runner`が`Core.exclusion_reason/3`で理由を付け、
結果の`"not_run"`に入れる。CLIはそれを`not run  <理由>`の行として出す(Old.md §33)。

`git_ctx/1` が `git rev-parse HEAD` / `git show -s --format=%cI HEAD` /
`git status --porcelain` を叩いて `commit`/`commit_at`/`dirty` を組み立てる
(gitが無ければ全部 `nil`、評価自体は止めない)。この後は §3 のコマンド実行
フローに合流し、method が `"eval"` なので次の §5 へ入る。

## 5. `"eval"` コマンドの中身 ── REPLへの実際の往復

これが一番ステップ数が多い。`XipeTotec.Runner.run_one/4` の `"eval"` 節から
`XipeTotec.Repl.Evaluator.run_pass/3` に入る。

```
Evaluator.run_pass(book, pass_id, opts)
  1. Core.plan_recalc(book, pass_id, call_ids: ...)          … 純粋。§6参照
       → 参照グラフ構築・循環検出・指定されたcallだけに絞る・effectフィルタ・topo_sort
       → Plan.Entry の列(module/name/args/inputs/basis/limits)
       → 加えて`plan.skipped`(2026-09-22新設、下記「skip経路」参照)
     entries が空なら{:ok, book, plan.skipped}で終わる(セッションは起動しない)。
     plan.skippedは結果として報告するだけで、Bookには書かない(評価していない
     ので記録しない、2026-09-26、Old.md §36)

  2. adapter = 4つの *_module オプション(既定は全部Elixir実装、§11参照 ──
     xipe_totec全体で言語による分岐が生じるのはここだけ)
       :launch_module        既定 XipeTotec.Repl.Launch
       :eval_template_module 既定 XipeTotec.Repl.EvalTemplate
       :scan_module          既定 XipeTotec.Repl.Eval.Scan.Direct.Iex
       :field_drip_module    既定 XipeTotec.Repl.Eval.FieldDrip.Elixir
     この4つと起動方法は、Runner が言語で選ぶ(2026-09-25): `SurfaceTable.
     rows(root, table_file)`の行(保存済みの table、2026-09-26)を使い、指定された行を関数 → ファイル →
     `language`とたどって言語ごとに分け、言語ごとにREPLを1つずつ起動する(2つ以上なら並行、
     2026-09-26、Old.md §39。呼び出し元が`:language`で1つに明示もできる。登録済みの言語が
     0個なら`no_language`。言語をまたぐ⟦id⟧参照の行は`not_run`)。各言語の`Repl.Language`モジュール
     (`Info.language_module/3`)の`adapter/0`が4モジュールを、`launch_opts/3`が
     起動方法を返す。呼び出し元が指定したモジュールや`:launch_opts`が優先。
     Elixirの`launch_opts/3`は、その言語の行の`build_tool`列(今この列を埋める
     のは<root>/mix.exs の有無だけ、Old.md §26.2)を見て mix-mode(空の
     `launch_opts`、`Launch`側の既定`iex -S mix`のまま)か scripts-mode かを決める。scripts-modeの
     `files`は table に載ったその言語のファイル(`launch_opts/3`の第3引数)を
     そのまま`-r`するのではなく、
     `SourceSanitize.sanitize/2`が`defmodule`部分だけの一時コピーを作った
     ものを使う(Fix Fと同じ理由 ── 原本をそのまま`-r`するとエントリー
     スクリプトのトップレベル副作用ごと実行されてしまう)。この関数は
     `{launch_opts, cleanup}`のタプルを返し、`cleanup`はセッション終了後に
     一時ディレクトリを消す(mix-mode/呼び出し元指定の場合は空振り)。

  3. adapter.launch.build(cwd: ..., interruptible: ..., ...)
       → JSON化可能なメッセージ %{"argv"=>,"env"=>,"cwd"=>,"files"=>,
         "ready_pattern"=>,"exit_input"=>,"interruptible"=>}
         (`interruptible`は2026-09-22新設。旧`heartbeat_interval_ms`/
         `heartbeat_input`はハートビート機構ごと撤去済み、下記6dの
         ハング判定を参照)

  4. sender.send(message)  (既定 XipeTotec.Repl.Sender.Direct)
       → :exec.run(argv, [..., {:group, 0}, ...]) でOSプロセスを
         **自分専用のプロセスグループに**起動(2026-09-22、`erlexec`移行)、
         handle(GenServer pid)を返す

  5. XipeTotec.Repl.Session.await_ready(sender, handle, message, timeout)
       → "Interactive Elixir" 等のready_pattern(バナー)が出力に現れるまで待ち
         (nilなら省略)、次にready_probe(IO.puts("XT_" <> "READY"))を送って
         "XT_READY" が出るまで待つ(nilなら省略)。timeoutは2段の合計
       (先に "XT_EXIT" が出たら起動失敗として即エラー、Old.md §35)

  6. Planの各entryについて順に:
       a. adapter.eval_template.build(entry)
            → 呼び出し式(module.name(args))がまず構文として完結しているか
              検査(Elixirなら Code.string_to_quoted/1)。**閉じていなければ
              対象言語へは一切送らず**、xipe_totec側で組み立てた診断文字列
              だけを印字する最小テンプレートを返す(build_syntax_error/3、
              2026-09-18) ── 完結していれば通常どおり対象言語のソース
              テキストを組み立てる(Elixirなら安全装置〈spawn_monitor+
              max_heap+timeout〉+ repr判定(a→b→c) + compare判定(basis参照)
              + マーカー印字、本文は複数回に分けず1回のIO.putsで出す
              〈2026-09-18、他プロセスの出力が割り込むのを防ぐため〉)
       b. sender.write(handle, そのテキスト)          … REPLの標準入力へ
       c. XipeTotec.Repl.Eval.Parser.step/5 のループで結果を待つ
            → adapter.scan.clean/1(トランスポート固有のノイズ除去、
              EXITマーカーの検出 ── ハートビートは2026-09-22に撤去済み) →
              汎用 Scan.scan/2(XT_BEGIN_<id>/XT_END_<id>またはXT_ERROR_<id>
              を検出) → 見つかったら adapter.field_drip.parse/1(repr=/
              type=/compare=/display=/bin_base64= の key=value 本文を読む)
              → Result.success/error/3 でCore.apply_results/3が期待する
              形に変換。**`XT_EXIT`が来た場合の専用処理は無い**(`cleaned.exit_status`
              は`adapter.scan.clean/1`が検出するが`wait_result`はこれを一切
              読まない) ── entry完了より前にセッションが予期せず終了した
              場合、単に何も届かなくなるだけなので下記dの固定デッドライン
              まで待ってから`session_hung`として扱われる(ラベルは不正確だが
              安全側には倒れる。外部レビュー2026-09-22で指摘、未修正のまま)
       d. entry開始時に固定した絶対デッドライン(entry.limits.timeout +
          既定2秒、`lib/repl/evaluator.exs`の`@default_deadline_padding_ms`。timeoutの既定5秒と合わせて合計既定7秒 ── Old.md §14.2追記の「既定7秒」はこの合計値)
          を過ぎたら「セッションがハングした」と判定 ── **受信のたびに
          リセットされる沈黙時間ではなく、固定の締切**(2026-09-18訂正:
          閉じていない式が対象言語側を入力待ちにし、それ以降に送った文字列
          を全部吸い込む状態でも、`after`が発火しないケースがあったため)。
          判定後(`end_hung_session/4`、2026-09-22新設):
            → `message["interruptible"]`が真なら、まず`sender.interrupt/1`
              (プロセスグループへSIGINT)を送り、短い猶予(既定2秒、
              `@default_interrupt_grace_ms`)だけXT_EXITの到着を待つ
            → 猶予内にXT_EXITが来なければ(または`interruptible`が偽なら)
              `sender.kill/1`(プロセスグループへSIGKILL)で強制終了
            → このentryは{:error,"session_hung"}、残り全entryは
              :abortedとして即座に打ち切る(interrupt/1が実際に効いても
              このentry自体の扱いは変わらない ── crux「option A」、
              同一セッションでの続行は見送り)

  7. 正常終了(ハングしていない)なら Session.close(sender, handle, exit_input)
       → exit_inputを書いてXT_EXITを待つ(graceful)→出なければ
         sender.kill(handle)で強制終了、それでも最終的にXT_EXITを待つ

  8. Core.apply_results(book, ctx, results)                 … 純粋。§6参照
       → 新しいBook(call行のresult/repr/compare/state等を更新)
```

**指定されたcallだけを評価する(2026-09-26、Old.md §36)**: Planに入るのは`call_ids`で
指定されたcallだけ。参照している下流も、参照されている上流も自動では加えない(Bookは
時系列の記録で、載るのはコマンドで指定した評価だけ)。REPLセッションは1回のpassの間だけ
保持するので、束縛がpassをまたぐことも無い。

**skip経路(2026-09-22新設、`Core.plan_recalc/3`側)**: 上記1.のPlan作成時点で、
解決不能な`:binding`参照(§6参照、値の無い参照先が同じpassで指定されていない、または効果の分類で外れた)を持つcallは`plan.entries`に入らず
`plan.skipped`(`{:skipped, ref}`outcome)へ回される。これはREPLを一切
経由せず、Bookにも書かない ── `Evaluator.run_pass/3`は結果の先頭で報告するだけで、
`plan.entries`が空ならセッションを起動しない。

**マーカープロトコル(§5で登場するテキスト規約)**:

| マーカー | 意味 |
|---|---|
| `XT_BEGIN_<id>` / `XT_END_<id>` | 評価成功、この間に `repr=`/`type=`/`compare=`/`display=`/(`bin_base64=`)の本文 |
| `XT_ERROR_<id> timeout` | entry自身のタイムアウト |
| `XT_ERROR_<id> max_heap` | max_heap超過によるkill(`:killed`理由の`:DOWN`から判定) |
| `XT_ERROR_<id> crash <reason>` | それ以外の例外 |
| `XT_EXIT <status>` | セッション終了、`Sender`実装が合成する(対象言語のテキストではない) |

これらの文字列そのものは対象言語が変わっても不変(`document/repl-adapter-guide.md`
の「変えてはいけないもの」)。

## 6. `Core.plan_recalc`/`Core.apply_results` の中身(§5のステップ1・8の詳細)

**`plan_recalc`(純粋、`lib/core.exs`)**:

```
1. reference_graph(book)           … 各callの args から ⟦id⟧ トークンを正規表現で抽出
2. cyclic_ids(graph)                … 循環にある call id の集合(評価対象から除外)
3. 指定されたcall(targets)のうち、存在し循環に入っていないもの(2026-09-26、下流を
   ⟦id⟧逆参照でたどって加えるaffected_setは削除した。Old.md §36)
4. filter_by_effect(book, requested) … effect_source=="user" かつ pure/reads(+writes任意)
                                       のみ残す(未分類ノードは絶対に実行しない)
5. topo_sort(scheduled, 循環を除いたグラフ)
6. 各idについて build_entry/3
     → args中の⟦ref⟧を resolve_ref/4 で置換:
          plan内で後から評価される参照      → :in_plan(束縛名プレースホルダ)
          既にexact/binaryな値がある参照     → その正規形テキストをそのまま埋め込む
          それ以外(このpassで束縛されない参照) → :binding(→ drop_unresolvableでskipped)
     → basis(compareの比較対象、spec §6.4のB決定ルール)を決める:
          call.prev_source=="user" かつ call.prev が空でない → {:exact, call.prev}
          (利用者がCore.set_prev/3で期待値を明示した場合を最優先。2026-09-18
          追加、Old.md §14.4)
          それ以外でcall.repr=="exact"→{:exact, call.result}
          それ以外でcall.repr=="binary"→{:binary, call.bin}
          それ以外→:none
```

**`apply_results`(純粋、`lib/core.exs`)**: `Evaluator`から返ってきた結果の列を
1件ずつ畳み込む。outcomeのタグ(`{:ok,%{...}}`/`:timeout`/`:max_heap`/
`{:error,reason}`/`{:skipped,id}`/`:aborted`)で分岐し、
`:ok`ならresult/repr/compare等を更新しつつ現在値を`prev`へ退避、
`{:skipped,id}`と`:aborted`は完全なno-op(評価していないので記録しない)。

**応答封筒(§17.2決定、2026-09-20)**: 通常の`{"jsonrpc","id","result"|"error"}`に
`"from"`(常に`null`の予約フィールド)と`"dialogue": {"hold","via_repl","text"}`

または今回で対話終了。`dialogue.via_repl`の意味は§17の2ビット表と向きが
逆なので注意(`Old.md` §17.2の訂正参照)。

**`input`（2026-09-27、Old.md §40）**: tezcatl の対話窓が打った1行をそのまま送る method。
`Serve.Socket`が横取りして`Serve.Input.start/3`へ渡す:

```
Serve.Input.start(line, state.dialogue)
  対話を保持中 → Dialogue.answer_params(mod, line) → Project.request_dialogue(…, "dialogue/answer", …)
  そうでなければ XipeTotec.Input.parse(line)       … 純粋。CLI と同じ書き方で読む
    {:text, _}（help/version）・:show・{:error, _}  → その場で返事（dialogue.text）
    {:commands, list}  → 別プロセスで1つずつ:
        Runner.substitute_command/2 で $<n> を解決
        → Project.request_dialogue(nil, method, params, watch: self())
        → 評価（repl な method）なら pass_id が返る → {:xipe_pass_done, pass_id, outcome} を待つ
        → 全部終わったら {:xipe_input_done, …} を Socket へ → 返事（OutcomeText の行を dialogue.text に）
```

評価を待つのは実行用のプロセスで、`Serve.Socket`の接続は待たない（ほかの要求に応える）。

対話を保持中の行は`Dialogue.line_request/2`で答え（または`quit dialogue` → `dialogue/quit`）にし、
`defer_commands: true`で`InOut`へ渡す。ターンが「この行を普通のコマンドとして」（`{:pass, …}`、検索の中で
打ったコマンド）や「終わったのでこのコマンドを」（`dialogue depends`の`y <値>`）を返したら、`InOut`は実行せず
`outcome.run`に載せて返し、`Serve.Input`が上と同じ実行用のプロセスで流す（評価回のキューを通る）。CLI の
`xipe search`は同じものを自分のプロンプトの中で`Runner.run/4`で流す（Old.md §41）。

§16の`eval/run`・`row/update`は`Pipeline`経由で、CLIでもサーバーでも動く
(2026-09-26、Old.md §37。サーバーでは非同期)。`xipe dialogue depends`のような対話プログラムは、
`Serve.Socket`側の複数ターン駆動ループへはまだ配線されていない(§17.3、
現状`InOut.run_to_completion/7`はCLI側`xipe dialogue depends`でのみ使われる)。

## 11. 言語による分岐と、Elixir固定の箇所(まとめ)

**言語で処理が分かれるように作ってある箇所は評価側**: `Evaluator`に渡す4モジュール
(`launch_module`/`eval_template_module`/`scan_module`/`field_drip_module`)と REPL の
起動方法は、surface table が示す言語の`Repl.Language`モジュールの申告
(`adapter/0`/`launch_opts/3`)から`Runner`が選ぶ(2026-09-25)。REPLは言語ごとに1つに
決め打ちで、ビルドツールは起動方法だけを変える。申告はElixir・OCaml・Haskell（2026-09-27、Old.md §42・§46。
HaskellはGHCiを`-ghci-script`で`embody.hs`と対象を`:load`して起動する。
OCamlは`Repl.Ocaml.Launch`が`ocaml -init <一時ファイル>`で起動し、一時ファイルが`embody.ml`と
対象のファイルを読み込む。`message["files"]`（`Sender.Direct`が`-r`にするiex用のもの）は使わない）。
`Evaluator`自身の既定値(Elixir用)は、Runnerを通らない直接の呼び出し(テスト)の
ためだけに残っている。

一方、**分岐の仕組みが無く、Elixirを前提に書かれている箇所**が別にある。多言語対応
(`課題.md` §1)で手を入れる対象はこちら:

| 箇所 | Elixir固定の中身 | 対応する課題 |
|---|---|---|
| Scanner の実装 | 選ぶ仕組み(`XipeTotec.Scanner` behaviour、言語の`scanner/0`で優先順)と、言語サーバー経由の共通実装`Scanner.Lsp`(2026-09-25)はある。dialect は Elixir(`Scanner.Lsp.Elixir`、elixir-ls)だけ。言語サーバーへは tezcatl の`/lsp`(`Lsp.Transport.Relay`)を先に試し、駄目なら自分で起動する(`Lsp.Transport.Stdio`)。予備の`Scanner.Elixir`は Elixir 専用 | `課題.md` §1 ⑥ |
| `Project.sheets/2`の除外 | `mix.exs`・`deps/`・`_build/`を言語に関係なく除外 | ②(ビルドツール層) |
| `SurfaceTable` | `repl`/`build_tool`はelixir行だけ判定(言語そのものは`info.json`の`extensions`から引くので固定ではない) | ② |

`Core`/`Book`/`Store`/`Dispatch`/`Pipeline`/`Session`/`Repl.Eval.Parser`/
`Repl.Eval.Scan`(REPL出力のマーカー検出の汎用部)/`Repl.Evaluator`は対象言語に
一切依存しない。

**`scan`という語の二義に注意**: `Scanner`/`scan/run`/`xipe scan`は「ソースから
定義を抽出する」側、`Repl.Eval.Scan`/`:scan_module`は「REPLの出力からマーカーを
検出する」側で、別物。
